## 1. 本阶段的唯一目标

> **让"它真的能在无人看管下 24 小时可靠地提醒我"这件事成立。**

因此本设计的**每一处复杂度都服务于三个数字**：

| 指标 | 目标 | 本设计的对应机制 |
| --- | --- | --- |
| 漏报 | **0** | 补偿窗口 + 持久化 occurrence + 崩溃恢复扫描 |
| 重报 | **0** | 数据库唯一键裁决 + 状态机 + 幂等 claim |
| 静默失败 | **0** | 所有失败必须落库 + 可见 + 可告警 |

## 3. daemon 启动序列（必须严格按序）

```
1. 解析 argv / 环境（--data-dir, --listen, --log-level）
2. 获取单实例锁            ← O_EXCL 创建 <data>/daemon.lock（含 pid + 启动时间）
     失败 → 探测已有 socket 是否响应 hello；响应则退出(已有实例)，不响应则清理陈旧锁继续
3. 载入 config.json（非敏感）+ 从钥匙串读取敏感项（M1 无敏感项，仅验证可用）
4. 打开 SQLite（WAL，busy_timeout=5000）+ 执行未应用迁移
5. 记录启动墙钟快照 wall_t0 与单调时钟 mono_t0
6. 检测时钟跳变：读上次关机的 last_seen_wall/mono → 计算 Δwall 与 Δmono
     Δwall 明显大于 Δmono（或反）→ 判定发生了 睡眠/挂起/改时间
7. ★ 补偿扫描（reconcile）：把所有 ≤ now+catchup 的未发 occurrence 入派发队列
8. 写启动审计 + run_log
9. 启动 tick 循环（§6.1）
10. 启动心跳写入（每 60s）
11. 打开 IPC 监听（UDS/NamedPipe，权限 0600）+ 写握手文件（含 token）
12. 标记 ready（写入 daemon.ready，UI 可探测）
13. 注册信号处理：SIGTERM/SIGINT → 优雅停止（停止 tick、等待在飞派发 ≤5s、释放锁）

崩溃兜底：捕获 uncaughtException/unhandledRejection → 记审计 → 退出码 1（由看门狗重启）
```

**为什么第 6 步单独做时钟检测**：睡眠恢复后 `setTimeout` 不会补发，且定时器漂移无法自证。用"双时钟差值"是**唯一能可靠判定"我睡了多久"**的方法，也是补偿逻辑的触发依据。

## 4. 数据表 DDL（M0+M1 全量）

> 命名：`snake_case`；时间统一存 **UTC 毫秒（INTEGER）**；枚举存 TEXT（可读、可迁移）；JSON 存 TEXT 并在应用层用 Zod 校验。

### 4.1 调度域（核心）

```sql
-- 提醒任务
CREATE TABLE task (
  id                TEXT PRIMARY KEY,              -- uuid v7（有序，便于索引）
  title             TEXT NOT NULL,
  notes             TEXT,
  priority          TEXT NOT NULL DEFAULT 'normal' -- normal | important
                    CHECK (priority IN ('normal','important')),
  enabled           INTEGER NOT NULL DEFAULT 1,
  -- 重复规则（NULL = 一次性）
  rrule             TEXT,        -- RFC5545 子集，如 FREQ=WEEKLY;BYDAY=MO,WE;INTERVAL=1
  dtstart_wall      TEXT NOT NULL,   -- 'YYYY-MM-DDTHH:mm:ss' 本地墙钟（不带时区）
  tzid              TEXT NOT NULL,   -- IANA，如 'Asia/Shanghai'：语义 = “在该时区的这个墙上时间”
  until_wall        TEXT,            -- 结束日期（含）
  count_limit       INTEGER,         -- 最多触发次数
  fired_count       INTEGER NOT NULL DEFAULT 0,
  -- 行为
  catchup_window_s  INTEGER NOT NULL DEFAULT 43200, -- 12h：错过补偿窗口
  snooze_default_s  INTEGER NOT NULL DEFAULT 600,
  dnd_override      TEXT NOT NULL DEFAULT 'inherit'  -- inherit | allow | block
                    CHECK (dnd_override IN ('inherit','allow','block')),
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL,
  deleted_at        INTEGER                          -- 软删除
);
CREATE INDEX idx_task_enabled ON task(enabled, deleted_at) WHERE deleted_at IS NULL;

-- ★ 触发实例：幂等性的唯一裁决点
CREATE TABLE occurrence (
  id                TEXT PRIMARY KEY,
  task_id           TEXT NOT NULL REFERENCES task(id) ON DELETE CASCADE,
  scheduled_at      INTEGER NOT NULL,   -- UTC ms（该实例的原定时刻）
  scheduled_wall    TEXT NOT NULL,      -- 冗余存墙钟，便于展示“原定 HH:MM”
  state             TEXT NOT NULL DEFAULT 'pending'
                    CHECK (state IN ('pending','claimed','delivered','failed','skipped','unknown')),
  claim_token       TEXT,               -- 派发者令牌（防重复领取）
  claim_expires_at  INTEGER,            -- 领取超时 → reconciler 处理
  attempt_count     INTEGER NOT NULL DEFAULT 0,
  delivered_at      INTEGER,
  last_error        TEXT,
  created_at        INTEGER NOT NULL,
  updated_at        INTEGER NOT NULL
);
-- ★★ 幂等基石：同一任务的同一时刻只能有一条实例
CREATE UNIQUE INDEX uq_occurrence ON occurrence(task_id, scheduled_at);
CREATE INDEX idx_occurrence_due ON occurrence(state, scheduled_at);
CREATE INDEX idx_occurrence_task ON occurrence(task_id, scheduled_at DESC);
```

### 4.4 关键约束的落地说明

| PRD 要求 | 本 DDL 如何保证 |
| --- | --- |
| FR-A4 绝不重复发送 | `uq_occurrence(task_id, scheduled_at)` 唯一索引；派发前 `UPDATE ... WHERE state='pending'` 影响行数=0 即放弃 |

## 5. 重复规则（RRULE 子集）与"墙钟语义"

### 5.1 语义决策（关键）

**决策**：任务的重复规则以**墙钟时间 + 时区**表达，而非固定 UTC 间隔。

| 场景 | 墙钟语义（采用） | 固定 UTC 语义（否决） |
| --- | --- | --- |
| "每天 9:00 提醒" 跨夏令时 | 始终本地 9:00 ✓ | 会漂到 8:00 或 10:00 ✗ |
| "每周一 10:00 站会" 跨时区出差 | 在任务时区的周一 10:00（可配置改跟随系统时区） | 意义不明 ✗ |

**实现**：`dtstart_wall + tzid` → 用 Temporal 计算 UTC 时刻；生成下一实例时**在墙钟域迭代**（`add({days:1})`），再转换 UTC。这样 DST 的 23/25 小时自然处理。

### 5.2 支持的 RRULE 子集（M1）

| 字段 | 支持 | 说明 |
| --- | --- | --- |
| `FREQ` | DAILY / WEEKLY / MONTHLY / YEARLY / HOURLY / MINUTELY | 覆盖 PRD 的每天/每周/每月/工作日/每 N 分·时 |
| `INTERVAL` | ✅ | 默认 1 |
| `BYDAY` | ✅（WEEKLY） | `MO,TU,WE,TH,FR` 即"工作日" |
| `BYMONTHDAY` | ✅（MONTHLY） | **31 号在小月自动跳过**（FR 已约定） |
| `BYMONTH` | ✅（YEARLY） | |
| `COUNT` / `UNTIL` | ✅ | 与 `count_limit`/`until_wall` 合并，取先到者 |
| `BYSETPOS` / `BYWEEKNO` / `BYYEARDAY` / `WKST` | ❌ 明确不支持 | 校验时报错并提示"用自定义间隔替代" |

**"每 N 分钟/小时"的锚定**：以 `dtstart_wall` 为锚点在墙钟域累加（不做 epoch 对齐），语义为"从我设定的时刻起每 N 分钟"——更符合直觉，且跨重启确定性一致。

### 5.3 求解器接口（纯函数，重点测试对象）

```ts
interface RecurrenceRule { rrule: string | null; dtstartWall: string; tzid: string; untilWall?: string; countLimit?: number }

/** 枚举 [fromUtc, toUtc] 区间内（含端点）的所有触发时刻，确定性、无状态、无 IO */
function occurrencesBetween(
  rule: RecurrenceRule, fromUtc: number, toUtc: number, cap = 1000
): Array<{ scheduledAt: number; scheduledWall: string }>;
```

- 上限 `cap` 防止"每 1 分钟 + 5 年区间"炸内存（超额则返回错误并记审计）。
- 一次性任务：`rrule = null`，仅返回 `dtstart_wall` 对应时刻（若在区间内）。

## 6. 调度状态机与核心算法

### 6.1 tick 主循环

```
每 TICK_MS = 30_000（可配）执行一轮：
  ① materialize()     把未来 LOOKAHEAD=24h 内的实例补进 occurrence 表
  ② dispatchDue()     把到期的 pending 实例派发出去
  ③ deliverPending()  处理 outbox 中的 notify.deliver
  ④ reconcile()       处理超时 claimed / 陈旧 inflight
  ⑤ housekeeping()    心跳、保留期清理、时钟跳变检测
每轮结束写 run_log（DEBUG 级），异常单独 try/catch，绝不因一个阶段失败而中断整个循环
```

**为什么 30 秒**：FR-A2 要求误差 ≤30 秒。tick 间隔即最坏误差上界，30s 满足且开销可忽略（空轮询只是几次索引查询）。

### 6.2 `materialize()` —— 生成实例（幂等）

```
窗口 = [now - max_catchup(全局最大补偿窗口), now + LOOKAHEAD]
for task in 启用的任务:
    for t in occurrencesBetween(task.rule, 窗口起, 窗口止):
        INSERT INTO occurrence(id, task_id, scheduled_at, scheduled_wall, state)
        VALUES (..., 'pending')
        ON CONFLICT(task_id, scheduled_at) DO NOTHING      -- ★ 幂等的第一道闸
    if task.count_limit 且 fired_count + 已生成数 >= count_limit:
        标记任务完成（enabled=0 需用户确认；不自动关闭一次性任务，保留历史）
```

- 窗口左端用"最大补偿窗口"是为了让**因长时间关机而错过的实例有机会被补**；但每个任务自己的 `catchup_window_s` 决定它**是否真的补发**（在 dispatch 时判断）。
- `ON CONFLICT DO NOTHING` 让重复运行完全安全：**materialize 可以每秒跑一次而不会产生重复**。

### 6.3 `dispatchDue()` —— 领取并派发（幂等的第二道闸）

```
候选 = SELECT * FROM occurrence
       WHERE state='pending' AND scheduled_at <= now
       ORDER BY (优先级 desc, scheduled_at asc) LIMIT BATCH=50

for occ in 候选:
    token = randomUUID()
    -- 原子领取：只有把 pending 改成 claimed 成功者才拥有派发权
    changed = UPDATE occurrence
              SET state='claimed', claim_token=token, claim_expires_at=now+60_000,
                  attempt_count=attempt_count+1, updated_at=now
              WHERE id=? AND state='pending'
    if changed == 0: continue                  -- 别人领走了 / 已发过 → 不重复
    if occ.scheduled_at + task.catchup_window_s < now:
        UPDATE occurrence SET state='skipped', last_error='beyond_catchup_window'
        continue                               -- 超出补偿窗口：记历史但不打扰（FR-A3）
    -- 事务内同时写通知与 outbox（保证“要么都写，要么都不写”）
    BEGIN
      notif_id = uuid()
      INSERT INTO notification(id, occurrence_id, kind='reminder', title, body,
                               priority=task.priority, scheduled_for=now, state='pending')
      INSERT INTO outbox(topic='notify.deliver', payload=json{notificationId: notif_id})
    COMMIT
```

**关键点**：`UPDATE ... WHERE state='pending'` 的**影响行数**是并发与重启场景下的唯一裁决依据 —— 不依赖任何内存标志。

### 6.4 `deliverPending()` —— 真正投递（含 DND、聚合、重试、兜底）

```
取 outbox 中 state='pending' AND next_attempt_at<=now ORDER BY next_attempt_at LIMIT 20
标记 inflight（乐观锁）→ 取对应 notification

1) DND 判定：
   若 当前处于免打扰时段 且 notification.priority 不是 high/urgent 且 task.dnd_override != 'allow':
       UPDATE notification SET scheduled_for = DND结束时刻, state='pending'（保留）
       outbox → done（等 DND 结束后由 materialize/dispatch 的“到期 pending 通知”阶段重新入队）
       ★ 不是丢弃，是推迟；DND 结束后若有多条 → 聚合成一条 catchup_batch
2) 渠道选择（M1：os_notification 主，cli_fallback 备；inapp 仅入库）
3) 尝试投递 → 写 delivery_attempt
4) 结果处理：
   success        → notification.state='delivered'；若由 occurrence 触发 → occurrence.state='delivered', delivered_at=now
   transient_error→ attempt+1，next_attempt_at = now + backoff(2^n * 2s, 上限 5min)；attempts > 5 → 降级到 cli_fallback
   permanent_error→ 立即降级到 cli_fallback；两者都永久失败 → notification.state='failed' + 生成 failure 通知（kind='failure'）
5) outbox → done
```

**降级链**：`os_notification` →（失败/超时）→ `cli_fallback`（macOS `osascript`）→ 仍失败 → 落库为 `failed` 并生成**关于失败的通知**（若连它都发不出，则下次成功投递时附带告知）。

### 6.5 `reconcile()` —— 崩溃/超时后的收敛（关键）

```
A. 超时 claimed：
   SELECT * FROM occurrence WHERE state='claimed' AND claim_expires_at < now
   → 说明：进程在“已领取、结果未知”时挂掉
   → 处理（FR-A4 的诚实版本）：
        state='unknown'，last_error='crashed_while_delivering'
        生成 system_gap 通知（dedupe_key='unknown:<occurrence_id>'，只发一次）：
        “有一条提醒可能已发出也可能没发（原定 HH:MM），请确认是否需要重新提醒”
        → 用户点“需要” → 创建一条一次性任务（新 occurrence），不复用原实例
B. 陈旧 inflight outbox：
   state='inflight' AND updated_at < now - 120s → 重置为 pending（下轮重试）
C. 运行缺口：
   检测 last heartbeat 与 now 的差 > 2*TICK_MS → 写 run_gap，生成 system_gap 通知
D. 时钟跳变：
   |Δwall - Δmono| > 60s → 变更 run_gap(cause='clock_jump') 并触发一次全量 materialize
```

> **⚠️ 诚实声明（必须写进产品说明与技术文档）**
> 跨"进程崩溃 + 操作系统通知系统"的**精确一次投递在理论上不可实现**（经典两将军问题：通知可能已显示但进程在记录前崩溃）。
> **本设计的保证是：**
> - **副作用最多一次**（绝不会重复弹出同一条提醒）——由唯一键与状态机保证；
> - **不确定状态显式暴露**，绝不静默猜测 —— `unknown` 状态 + 一次性询问用户。
> 这比"看起来永不重复但偶尔静默丢失"更强：**宁可问一次，也不假装确定。**

### 6.6 `watchdog`（Electron 侧）+ 心跳（daemon 侧）

| 层 | 机制 |
| --- | --- |
| Electron Main | 每 5s ping daemon（IPC `sys.health`）；连续 3 次失败 → 记录 + 尝试重启 daemon（≤3 次/10 分钟，超限则只告警不狂重启） |
| daemon | 每 60s 写 heartbeat（含 rss/fd）；检测自身与上次心跳间隔异常 → 写 run_gap |
| 用户可见 | 菜单栏图标变色（正常/降级/异常）；主界面顶部状态条显示"上次检查 / 下次提醒 / 今日已发" |

| C-2 | vec0 表的主键/rowid 绑定**必须用 BigInt**（`1n`），用 JS number 会报 "Only integers are allows for primary key values" | 向量写入失败，且错误信息不提示类型 |

| C-4 | IPC 客户端**每次重连都必须重放 `sys.hello` 握手**（新连接 = 新鉴权会话） | 重连后所有调用被 `E_AUTH` 拒绝 |
| C-5 | 钥匙串读取必须带 `-w`（不带会走 GUI 授权对话框，无人值守场景会卡死）；`security` 的钥匙串路径必须是**最后一个位置参数** | 24/7 场景凭据读取阻塞 |
| C-6 | 开发环境需固定 Node 版本（DSH 随附的 v24.21 开启库校验，会导致 Vitest 无法加载 rollup 原生模块） | 本地测试无法运行 |
| C-7 | **任何依赖安装的验证/测试，工作目录必须在 pnpm 工作区之外** | pnpm 会向上继承仓库 lockfile/node_modules，导致间歇性失败与"单独跑通过、整套跑失败"的不可信结论 |
| C-8 | **能力探测必须与真实路径同构**（真的写 plist / 真的 bootstrap），不要用代理命令（如 `launchctl submit`） | 代理命令的失败模式与真实路径不同，会产生误判 |
