## 1. 背景与问题

### 1.1 现状

个人日常事务的"记得做"和"及时知道"，以及"把活干完"，目前散落在很多互不相通的工具里：

- 提醒靠系统日历 / 备忘录 / 手机闹钟 —— 只认固定时间点，不会**理解内容**。
- 信息获取靠手动刷 —— 邮箱、IM、RSS、商品页面、项目目录、系统状态，都得人主动去看。
- 自动化靠零散脚本 —— 写的时候记得，过两周就忘了它存在，也没有统一的通知、日志和收敛机制。
- 通用 AI 助手是**被动且无角色**的 —— 你不问它不说；关掉窗口就停止工作；每次对话都从零开始，不承担任何持续责任。
- 单个 AI 助手做不完整条链路 —— "写 PRD → 开发 → 测试 → 修 bug → 回归 → 验收"这种活，一个对话窗口做不完，也没人盯着它做完。

### 1.2 核心痛点

> **电脑在 24 小时运行，但我既没有一个替我"看着"的哨兵，也没有一支替我"干活"的团队。**

具体表现为六类损失：

1. **错过**：重要邮件、日程冲突、会议前 10 分钟、家人交代的事，看到时已经晚了。
2. **遗忘**：脚本/任务写了但没跑、跑了但失败了、失败了没人知道。
3. **重复劳动**：每天早上手动查日程 + 待办 + 天气 + 项目状态，每天 10 分钟，一年 60 小时。
4. **噪音**：为了不错过而开启所有推送，结果重要信息被淹没，最后全部静音。
5. **精力碎片化**：一件完整的活（写文档、改代码、跑测试）需要我在多个上下文之间来回切换，每个环节都得我亲手推一下。
6. **隐私焦虑**：想让 AI 帮忙处理真实的工作内容（客户信息、代码、合同），但不敢把原文直接交给第三方模型。

### 1.3 机会

一台常开的个人电脑 + 本地大模型/API + 桌面常驻能力，可以做出两件过去做不到的事：

- **一个有判断力的哨兵**：它替我盯着所有信息源，在该说话的时候只说该说的话。
- **一支有角色、能协作的员工团队**：它们分工明确、能把活从一个人手里交到另一个人手里、能自己验证结果、能在我不在的时候继续推进，并且**经过脱敏之后**才把数据交给模型。

关键差异不在于"模型多强"，而在于：**有角色、有流程、会交接、可验证、可审计、会成长。**

### 1.4 一个必须正视的矛盾（本版新增）

新增的多 Agent 协作能力，与 v0.1 的"单用户可信哨兵"在**信任模型上是相反的**：

| 维度 | 哨兵层 | 员工层 |
| --- | --- | --- |
| 行为特征 | 确定性、可预测、幂等 | 概率性、创造性、会犯错 |
| 运行模式 | 长驻低耗、空闲几乎为零 | 任务驱动、突发高耗 |
| 主要风险 | 漏报、误报、打扰 | **幻觉、乱改文件、烧钱、无限循环、越权** |
| 信任来源 | 规则可验证 | 必须靠**机械验证 + 人工审批门** |

**结论：两者必须是分层架构，共用同一套内核（安全/审计/通知/Skill/模型网关），但绝不混在同一个进程、同一套权限里。** 详见第 3 章与第 7 章。

## 2. 产品定位

### 2.1 一句话定义

> **一个安装在桌面、24 小时常驻的个人 Agent 工作台：底层是替我盯着世界的哨兵，中层是一支有明确角色、可并行工作、能把活互相交接直到交付的员工团队，顶层是多个各负责一个项目的团队（团队之间通过显式接口契约协作）；所有外发给模型的数据都经过脱敏网关。**

### 2.2 三层形态

```
┌──────────────────────────────────────────────────────────┐
│  第三层：组织层（Organization）                             │
│  多个团队 · 每团队一个项目 · 跨团队接口契约 · 三层并发与预算   │
│  例：博客团队 ⇄ 设计团队 ⇄ 数据分析团队                       │
└──────────────────────────────────────────────────────────┘
                          ▲ 共用内核 ▼
┌──────────────────────────────────────────────────────────┐
│  第二层：员工层（Agent Employees）                          │
│  岗位定义 · 多 Agent 并行 · 任务看板 · 交接协议 · 验证门      │
│  例：产品经理 → 前端/后端 → 测试 → 回归 → 产品验收            │
└──────────────────────────────────────────────────────────┘
                          ▲ 共用内核 ▼
┌──────────────────────────────────────────────────────────┐
│  第一层：哨兵层（Sentinel）                                 │
│  定时提醒 · 监测信息源 · 判断轻重 · 多渠道通知 · 心跳自监控     │
└──────────────────────────────────────────────────────────┘
┌──────────────────────────────────────────────────────────┐
│  共用内核：脱敏外发网关 · 凭据管理 · 审计 · Skill · 调度 · 存储 │
└──────────────────────────────────────────────────────────┘
```

**为什么是这个顺序**：员工干活需要有人知道进度、需要有人被通知"卡住了"、需要定时巡检 —— 哨兵层既是独立价值，也是员工层的基础设施。而团队协作要求"一个团队内部先能跑通"，否则多团队只是把混乱放大。**先做哨兵不是妥协，是依赖关系。**

### 2.3 它是什么

| 维度 | 说明 |
| --- | --- |
| 形态 | 桌面常驻应用（macOS 菜单栏 / Windows 托盘 / Linux 托盘），可无界面后台运行 |
| 主动性 | 哨兵主动监测通知；员工主动领取任务、交接、推进 |
| 多 Agent | 支持同时运行多个 Agent，各自独立的工作区、权限、凭据、预算，互不污染 |
| 多团队 | 支持创建多个团队，每个团队负责一个指定项目；团队之间通过显式接口契约协作，默认互相隔离 |
| 组织视角 | 一屏看到所有团队在干什么、谁在等谁、卡在哪、各花了多少 |
| 角色化 | 每个 Agent 是"我的一个员工"：有岗位、职责边界、禁止事项、交付物标准、预算 |
| 协作 | Agent 之间通过**任务看板 + 交接协议**传递工作，支持返工、回归、升级 |
| 判断力 | 规则保证可靠性，LLM 保证语义理解与生成能力 |
| 隐私 | **任何外发数据先过脱敏网关**；分级、可逆占位符、会话级一致、敏感内容默认拒答（v1.0 无本地模型，见技术架构 §5.1） |
| 可扩展 | 内置默认证哨兵 Skill 与默认岗位模板，支持导入/上传自定义 |
| 会成长 | 记录反馈与结果，逐步调低噪音、调高命中率、调优岗位提示词 |
| 数据位置 | 默认**全本地**；外发内容可见、可裁剪、可拦截、可全关 |

### 2.4 它明确不是什么（防止范围蔓延）

- ❌ **不是通用聊天助手**：不做开放式对话产品，对话只是下达任务与审批的入口。
- ❌ **不是团队协作工具**：单用户、单机优先，不做多人共享、不做组织权限体系。
- ❌ **不是云端服务**：不做服务端账号体系；跨设备同步是「以后可能」级别。
- ❌ **不是移动 App**：手机端只作为**通知接收端与审批入口**。
- ❌ **不是无人工介入的全自动公司**：**关键节点必须有人审批门**。"全自动流水线"不是目标，"我不用盯但随时能管"才是目标。
- ❌ **不做模型训练/微调**：只做提示词、参数、偏好的调整。
- ❌ **不自建日历/邮箱/IM/代码托管**：只做聚合、编排与判断层。
- ❌ **不做对外服务的 Agent 平台**：外部 Agent 接入（A2A/MCP）是以后可能项，不是本期目标。

#### 2.4.1 关于「登录页 / 账号体系」的明确否定（v0.7 补充）

这一条单独成节，因为它是本项目**最容易被误解、也最容易在实现时被"顺手加上"**的设计决定。

> ## ❌ 本项目**没有登录页，也不做账号体系**。
> 它的唯一身份就是"使用这台电脑的人"。没有注册、没有登录、没有服务端会话、没有云端账号。

**为什么这是硬约束，而不是"暂时没做"：**

| 若引入登录门 | 违反的需求 | 后果 |
| --- | --- | --- |
| 未登录不能启动 | **NFR-R4**（断网下定时提醒 100% 可用） | 断网/服务端故障 = 提醒全部失效 |
| 启动需联网校验 | **NFR-R1**（连续运行 30 天）、**NFR-R2**（崩溃自恢复） | 重启后若认证失败，进程活着但**静默不工作** —— 本项目最想避免的失败模式 |
| 需要账号服务端 | PRD §2.3「不是云端服务」 | 产品性质从"私人工具"变成"SaaS"，引入运维、找回密码、封禁申诉等一整套负担 |
| 登录态存在本地 | **NFR-S1**（凭据只进钥匙串） | 多一个可被窃取的会话凭据，安全面反而变大 |

**这不是隐私上的让步。** 隐私保护在本项目中由另外三条机制承担，它们都不依赖账号：

1. **数据默认全本地**：SQLite 单文件 + 内容寻址 blobs，不出机器（§8.4）
2. **外发必须先脱敏**：唯一出口 + fail-closed，敏感内容默认拒答（§8.2 / FR-S13）
3. **操作系统用户隔离**：不同 macOS 账号 = 不同数据目录，天然隔离

**唯一存在的"身份"机制是可选的本机口令锁**（见 FR-S25）：
它只用于"防止同一台电脑上的其他人翻看我的提醒与数据"，**不联网、不校验服务端、不影响后台提醒**。

> **给实现的红线**：任何形式的"登录/注册/账号绑定"都不属于本项目范围。
> 如果某个功能（如同步、云备份）需要它，那个功能应当被砍掉，而不是把账号体系引进来。

### 2.5 设计原则

1. **可靠优先于聪明**：定时提醒绝不能因为 LLM 超时/失败而不响。规则路径必须是不依赖网络的独立通路。
2. **验证优先于信任**：任何 Agent 说"我完成了"都不算完成，必须有机械验证证据（编译通过、测试通过、校验通过）。**禁止 Agent 之间互相点赞式确认。**
3. **数据出门先脱敏**：外发是特权，不是默认。默认保守（按高敏感处理），可逆占位符保证脱敏不降可用性。
4. **最小权限、按角色隔离**：员工只能碰职责范围内的东西；越权在引擎层拒绝，不只靠提示词约定。
5. **一切可解释、可追溯**：每条通知、每个结论、每次交接都能回答"依据是什么"。
6. **人是最终决策者**：不可逆、对外、花钱、动主干的动作必须经过审批门。
7. **安静是默认状态**：没有值得说的事，就什么都不说。
8. **成本是一等公民**：每个员工有预算，超限自动降级/排队/上报，不允许静默烧钱。
9. **可卸载、可带走**：数据用开放格式（SQLite + YAML/JSON + 标准 Markdown 交付物），不锁定。

## 3. 术语表

| 术语 | 定义 |
| --- | --- |
| **内核（Core）** | 与业务无关的基础设施：脱敏网关、审计、凭据、Skill、调度、存储、通知总线 |
| **哨兵层（Sentinel）** | 主动监测 + 通知子系统，长驻低耗 |
| **员工层（Workforce）** | 多 Agent 执行与协作子系统，任务驱动 |
| **Monitor（监测器）** | 一类数据源的适配器，如 FileMonitor / WebMonitor / MailMonitor |
| **Signal / Fact / Event** | 原始信号 → 去重归一化后的事实 → 命中规则的待判断事件 |
| **Policy（策略）** | 判断规则：条件（when）→ 动作（then），可含 LLM 判断步骤 |
| **Skill（技能）** | 可复用能力包 = 触发器 + 策略 + 动作 + 提示词模板 + 默认参数 |
| **Role（岗位）** | 员工的角色定义：职责、禁止事项、可用工具/知识、交付物标准、交接规则、预算 |
| **Employee（员工）** | 一个被创建出来的、绑定某个 Role 的 Agent 实例（含模型、工作区、凭据作用域、预算） |
| **Team（团队）** | 一个**项目单元**：为一个指定项目负责，含成员（员工）、流程模板、预算、对外接口 |
| **Team Template（团队模板）** | 可一键实例化一个团队的定义包 = 岗位集合 + 流程模板 + 对外接口约定 |
| **Team Interface（团队接口）** | 团队对外的声明式契约：能提供什么服务、需要什么输入、验收标准、响应时限 |
| **Cross-Team Handoff（跨团队交接）** | 跨团队边界的交接单，额外记录团队归属、SLA 计时、责任人与预算归属 |
| **Shared Resource（共享资源）** | 被显式授权在多个团队间复用的员工或工具（默认**不允许**共享） |
| **Team Budget（团队预算）** | 团队级成本上限；与员工级/全局级共同构成三级预算 |
| **Workflow Template（流程模板）** | 声明式交付流水线：阶段、执行角色、完成定义(DoD)、失败处理、审批门 |
| **Task（任务）** | 看板上的一张工作项（含类型、负责人、状态、交付物、历史） |
| **Handoff（交接）** | 一个员工把任务连同交付物、结论、遗留问题交给下一个角色 |
| **DoD（完成定义）** | 某阶段"算完成"的机械可验证条件（测试通过、构建成功、格式校验通过等） |
| **Gate（审批门）** | 需要人明确放行才能继续的节点（如合并主干、对外发布、花钱） |
| **Artifact（交付物）** | 任务的产出物（PRD.md、代码提交、测试报告、验收单），带版本与来源 |
| **Verification（验证）** | 对交付物的机械检查，不依赖任何 Agent 的主观判断 |
| **Run / Step** | 员工的一次执行 / 执行中的一个动作步 |
| **Budget（预算）** | 员工或任务的资源上限（token、金额、时长、工具调用次数） |
| **Escalation（升级）** | 无法继续时上报给人（含原因、已尝试路径、建议选项） |
| **Redaction Gateway（脱敏外发网关）** | 所有外发模型请求的唯一出口，负责分级、检测、脱敏、占位、还原、审计 |
| **Data Class（数据分级）** | L0 公开 / L1 内部 / L2 敏感 / L3 机密凭据 |
| **Placeholder Map（占位映射）** | 本地持有的 `[EMAIL_1] → 真实值` 映射表，用于模型返回后还原 |
| **Feedback（反馈）** | 用户对通知的显式反应（有用/无用/稍后/不再提醒）或隐式反应 |
| **Quiet Hours** | 免打扰时段，普通通知聚合延后，高优先级可穿透 |
| **Software（软件）** | 被登记进能力清单、可被员工调用的本地/沙箱应用程序 |
| **Capability Manifest（能力清单）** | 软件的登记卡：能做什么、怎么调、需要什么权限、数据去哪 |
| **Invocation Mode（调用方式）** | CLI/API · 应用内自动化（AppleScript/VBA/插件） · GUI 自动化；越靠右越脆弱 |
| **SoftwareRequest（软件申请）** | 员工请求安装新软件/扩展/包的结构化申请单 |
| **Source Allowlist（来源白名单）** | 允许获取软件的可信来源；**来源比软件名更重要** |
| **Sandbox（沙箱环境）** | 员工运行软件与依赖的隔离环境（独立目录/虚拟环境/容器） |
| **Manual Guide（操作引导）** | 无法或不宜自动化时，员工给我手动执行的步骤清单（人机接力） |
| **Knowledge Base（知识库）** | 分层（个人/团队/组织/外部）的可检索知识集合，每条带数据分级标签 |
| **RAG** | 检索增强生成：先检索有依据的片段，再让模型基于片段回答/做事 |
| **Chunk（知识块）** | 知识的最小检索单元，保留来源位置（文件 + 行号/页码）与内容哈希 |
| **Hybrid Retrieval（混合检索）** | 向量检索 + 关键词（BM25）双路召回 + 重排 |
| **Citation（引用）** | 结论对应的知识来源指针；结论必须可溯源 |
| **Context Layers（上下文四层）** | 锚定层 / 受保护事实层 / 工作层 / 历史层，压缩策略各不相同 |
| **Context Compression（上下文压缩）** | 上下文接近窗口上限时，把工作层摘要化、历史层移出并落快照 |
| **Snapshot（上下文快照）** | 压缩前的完整上下文存档，可查看、可对比、可回滚 |

## 5. 范围与分期规划

### 5.1 分期总原则

你明确说了"**所有的都需要，但一步一步来，先做最简单的，能正常投入使用后再一点点开发**"。因此：

1. **M1 只有一个目标：让"它真的能 24 小时可靠地提醒我"成立。** 不接 LLM、不接邮箱日历、不做员工。可靠的地基没打好，上面全是沙子。
2. **M0 是安全地基，必须在第一个 LLM 调用之前完成。** 脱敏网关不是"以后再加"的功能 —— 一旦有明文出过门，就收不回来了。
3. **员工层的能力顺序不能颠倒**：先"单个员工能干活"（M4），再"多个员工能协作"（M5）。一个员工都干不明白就上团队，只会得到一群互相点头的机器人。
4. **每个里程碑以"我自己每天在用"为验收门槛。** 没有真实使用的功能不算完成，不进下一期。
5. **上期不稳定，不开始下期。**

### 5.3 M0 范围界定（安全地基，新增）

**做：**

- 数据分级模型（L0–L3）与默认分级策略（默认保守：未知→L2）
- 敏感信息检测器：身份证、手机号、银行卡、邮箱、地址、IP、API Key/Token、私钥、连接串、自定义关键词
- **可逆占位符机制**：`[EMAIL_1]`、`[ID_1]` 等，会话内一致，返回后本地还原
- 外发审计：每次出站记录（时间、员工、目标模型、脱敏项、策略版本、请求哈希、响应状态）
- 凭据管理：Key 一律进系统钥匙串，绝不落配置文件
- 模型 Provider 抽象骨架（OpenAI 兼容 / Anthropic / Ollama）
- **数据不出机器模式**：全局开关 + 按员工开关

**不做：** ❌ 任何业务功能 ❌ 界面美化 ❌ 图像/语音内容的脱敏（列入 M3 之后）

> **M0 的硬约束**：在 M0 验收通过之前，**不允许任何真实数据被发送到任何外部模型**。测试只能用构造的样本。

### 5.4 M1 范围界定（提醒内核）

**做：** 常驻进程 + 菜单栏、一次性/每天/每周/每月/工作日/自定义间隔提醒、通知（横幅+声音）、稍后提醒、休眠与关机后的错过补偿、幂等保证、开机自启与崩溃自恢复、本地 SQLite 持久化、最小界面（任务列表/新建编辑/历史/暂停）、配置与数据导出备份

**不做：** ❌ 任何 LLM 调用 ❌ 日历/邮箱/IM ❌ 手机推送 ❌ Skill 上传 ❌ 员工层

> **M1 的关键约束**：必须能在**完全断网**下 100% 正常工作。

```
                                    │
M1/M2/M3 ──────────────────────────┴──► M4 员工层的地基
                                          （通知=汇报、监测=进度巡检、Skill=岗位能力）
M4 单员工能干活 ──► M5 单团队能协作 ──► M6 多团队与跨团队协作
                    （一个员工都干不明白 → 别上团队）
                                      （一个团队都跑不通 → 别上多团队）
M5/M6 ──► M7 学习（有稳定流程才有可优化信号；跨团队信号更稀疏，必须后置）
```

## 6. 功能需求详述

### 6.1 模块 A：提醒与调度（M1）

**FR-A1 创建提醒**：一次性 + 重复（每天 / 每周指定星期 / 每月指定日 / 工作日 / 每 N 分钟·小时·天），支持结束日期或次数。

**FR-A2 精确投递**：正常运行误差 ≤ 30 秒；休眠导致的延迟不计失败，但恢复后必须补偿。

**FR-A3 错过补偿（关键）**：进程未运行期间到期的提醒，在恢复后 **60 秒内**补发并标注"（错过，原定 HH:MM）"；补偿窗口可配（默认 12 小时，超出只记历史不发通知）；补偿多条时**合并为一条摘要**，避免一次弹 20 条。

**FR-A4 幂等保证**：同一提醒实例绝不重复发送，唯一键为 (任务 ID + 计划触发时刻)。

**FR-A5 稍后提醒**：通知上直接"10 分钟 / 1 小时 / 今晚"；产生新实例，不影响原重复规则。

**FR-A6 完成与跳过**：重复任务只影响当前实例。

**FR-A7 暂停与免打扰**：全局暂停、按任务静音、免打扰时段；DND 期间普通提醒延后合并，重要提醒可穿透（可配置）。

**FR-A8 通知内容**：标题、正文、来源标签、触发理由、操作按钮。

**FR-A9 自然语言创建（M3）**：如"每周三下午提醒我给妈妈打电话"，生成草稿，**用户确认后**才落库。

### 6.2 模块 B：监测管道（M2–M3）

统一管道，所有监测器实现同一接口，新增数据源不改内核：

```
采集(Signal) → 归一化 → 去重/变化对比 → (Fact) → 规则匹配 → (Event) → 判断 → (Notification)
```

**FR-B1 监测器接口**：声明采集周期、产出字段、所需权限；支持单独启停与限流。
**FR-B2 文件与目录监测（M2）**：新增/修改/删除/重命名，支持 glob、忽略规则、稳定期判定（避免半截文件）。
**FR-B3 网页与订阅监测（M2）**：URL / RSS / Atom，支持 CSS 选择器或 JSONPath 定位，**仅在内容真正变化时**产生事实（含 diff 摘要），失败重试 + 连续失败告警。
**FR-B4 系统健康监测（M2）**：CPU、内存、磁盘、网络、电量、进程存活、端口可达；阈值 + **滞回**避免抖动告警。
**FR-B5 日历与待办（M3）**：系统日历 / Google Calendar / CalDAV；会议前提醒、冲突检测、日报聚合。
**FR-B6 邮箱与消息（M3）**：IMAP 或 Gmail API；发件人/主题/关键词预筛 + LLM 判断重要性；**默认只读**，不做自动回复。
**FR-B7 去重与变化对比（M2 核心）**：内容指纹 + 冷却期（默认 24 小时，可配）；内容未变不通知。
**FR-B8 限流与聚合**：单监测器每小时上限；同类通知窗口内合并为摘要。

### 6.3 模块 C：Skill 与策略引擎（M2）

**FR-C1 Skill 格式**：人类可读可写的 YAML —— 元信息（名称/版本/作者/描述/所需权限）、触发方式、条件、动作、提示词模板、默认参数。示例（示意语法）：

```yaml
name: disk-space-guard
version: 1.0.0
description: 磁盘剩余空间低于阈值时告警
permissions: [system.read]
params:
  threshold_percent: 10
  cooldown: 6h
trigger:
  type: threshold
  monitor: system.disk
  field: free_percent
  op: "<"
  value: "{{params.threshold_percent}}"
action:
  notify:
    priority: high
    title: "磁盘空间不足"
    body: "{{monitor.mount}} 剩余 {{monitor.free_percent}}%（{{monitor.free_gb}} GB）"
```

**FR-C2 内置默认技能包**：会议前提醒、磁盘告警、下载目录整理提示、每日早报、RSS 摘要、进程守护。默认技能必须在**零 API Key** 下可用（纯规则版），配置 Key 后自动升级为 LLM 增强版。
**FR-C3 导入与上传**：从文件/URL/粘贴导入；导入时**展示将要启用的权限与动作**并要求确认；版本与冲突提示。
**FR-C4 校验与干跑**：语法 + 权限校验 + dry-run 预览（"如果现在跑会发什么通知"），避免导入即刷屏。
**FR-C5 自然语言生成 Skill（M3）**：描述需求 → 生成 YAML 草稿 → 展示 diff 与权限 → 确认后启用。
**FR-C6 自定义动作**：M2 起仅"通知类"；脚本执行与软件调用能力在 M4 且必须显式授权 + 超时 + 输出捕获 + 失败告警（详见 §7.14 软件能力与安装治理）。

### 6.4 模块 D：判断与投递（M3）

**FR-D1 规则 + LLM 混合判断（铁律）**

| 阶段 | 由谁负责 | 失败时行为 |
| --- | --- | --- |
| 是否到时间 / 是否达阈值 | **规则**（纯本地） | 不可能失败 |
| 内容是否变化 / 是否重复 | **规则**（本地去重） | 不可能失败 |
| 这件事重不重要 / 值不值得打断 | **LLM**（可关） | 降级为规则默认结论 |
| 怎么说 / 摘要成几句话 | **LLM**（可关） | 降级为模板文案 |

> **LLM 只参与"判断"和"表达"，绝不参与"是否按时触发"。** 断网、超时、超预算一律降级为纯规则。

**FR-D2 LLM Provider 抽象**：OpenAI 兼容 / Anthropic / DeepSeek 等云端为主；**本地 Ollama / LM Studio 作为可选 Provider 保留接口但 v1.0 不实现**（见技术架构 §5.1）。可配模型、超时、重试、单日调用与成本上限；超限自动降级为纯规则模式**并告知用户**。
**FR-D3 最小外发**：见第 8 章脱敏网关（本版强化）。
**FR-D4 通知渠道（M3）**：系统通知、Webhook、Bark、Telegram、邮件(SMTP)、TTS；支持按优先级/类型分流。
**FR-D5 投递可靠性**：各渠道独立重试（指数退避），失败降级到系统通知，绝不丢通知。
**FR-D6 聚合与摘要**：非紧急通知窗口聚合；每日/每周摘要（含"本周它帮你避免了什么"）。

### 6.5 模块 E：反馈与自学习（M7）

**FR-E1 通知内联反馈**：有用 / 没用 / 稍后 / 这类别再提醒。
**FR-E2 隐式反馈**：是否点开、停留时长、是否立刻静音、是否手动完成。
**FR-E3 偏好画像（本地、可查看可编辑）**：人类可读形式存本地，用户可直接改。
**FR-E4 阈值自调整**：在规则允许的边界内微调，且必须可追溯（"因为你在 5 次类似通知里都点了没用，我把冷却从 24h 调到 72h"）。
**FR-E5 学习安全边界（铁律）**

- 学习**只能调整参数、优先级、措辞与 DoD 建议**；**不得**新增数据源、提升权限、新增外发渠道、放宽脱敏级别、跳过审批门。
- 所有自动调整留痕，可一键回滚。
- 任何会导致漏报的调整必须可见、必须显式提示。
- 员工层的学习只能改提示词与流程参数，**不得自动降低验证强度**。

**FR-E6 升级机制**：反复被忽略的重要事项自动升级；已确认完成的事项停止提醒。

### 6.6 模块 F：界面与交互（贯穿）

- **菜单栏/托盘**：存活状态、今日剩余提醒、下次提醒倒计时、快速暂停、快速派活、打开主界面。
- **主界面**：任务列表 / 监测器状态 / Skill 管理 / **员工列表** / **任务看板** / **软件能力与软件申请** / 通知历史 / 审计日志 / 预算面板 / 设置。
- **首次启动向导**：3 步内可用（语言 → 是否开启 LLM 及外发级别 → 是否开机自启），不做强制注册。
- **状态透明**：随时能看到"它在做什么、上次检查时间、下次要做什么、今天花了多少"。
- **失败可见**：监测器失败、渠道失败、LLM 失败、员工卡住，必须在界面显示，不许静默。

## 7. 模块 G：多 Agent 员工与协作系统（M4–M5，本版新增核心）

### 7.1 设计目标

把"一个被动对话助手"升级为"一支有岗位、有边界、有交付标准、能互相接力的员工团队"，同时做到：

- 员工**知道自己是干什么的**（岗位职责边界）
- 员工**不敢乱来**（权限与工具隔离）
- 员工**不会瞎说自己做完了**（机械验证）
- 员工**能接力**（交接协议 + 看板）
- 员工**会停下来找我**（预算、升级、审批门）
- 员工**崩了不丢活**（持久化 + 幂等 + 恢复）

### 7.2 员工（Employee）定义模型

一个员工实例必须显式声明以下要素，缺一不可：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| **岗位（Role）** | 角色名与一句话职责 | 前端工程师：实现界面与交互 |
| **职责范围（Scope）** | 做什么（正向清单） | 写前端代码、自测、提测 |
| **禁止事项（Prohibited）** | 明确不能做什么 | 不改数据库 schema、不动 CI 配置、不合并主干 |
| **工具集（Tools）** | 允许使用的工具与命令白名单 | 文件读写、git、包管理器、测试命令、搜索 |
| **软件范围（Software Scope）** | 允许调用的软件清单与调用方式上限 | Excel/CLI 只读；浏览器仅查询；**不含 GUI 自动化** |
| **安装权限（Install Rights）** | 是否能发起软件申请、能否装进沙箱、是否需逐次审批 | 可申请不可自装；沙箱内可装；主环境需审批 |
| **知识源（Knowledge）** | 可读的目录/文档/外部源 | 项目 repo、设计稿目录、接口文档 |
| **交付物标准（DoD）** | 机械可验证的完成条件 | `pnpm build` 通过 + 单测全绿 + lint 无 error |
| **交接规则（Handoff）** | 成功后交给谁、失败后回给谁 | 成功→测试工程师；失败→回自己重试（≤3 次） |
| **预算（Budget）** | token / 金额 / 时长 / 工具调用上限 | 单任务 $1.5、30 分钟、200 次工具调用 |
| **模型档位** | 用哪个模型（成本与能力权衡） | 强模型 / 中模型 / 本地模型 |
| **外发级别** | 允许外发的数据上限 | L1（可脱敏外发）/ 仅本地 |

**FR-G1 岗位可创建、可修改、可复用**：可从模板库导入，可自定义，支持导出分享。
**FR-G2 员工实例化**：一个岗位可以有多个员工实例（如"前端 A""前端 B"），各自独立工作区、预算、凭据作用域。
**FR-G3 岗位提示词可编辑**：用户改完即生效，并有版本记录与回滚（对应 UW-13）。
**FR-G4 员工卡片**：在主界面能以卡片形式看到每个员工的岗位、状态、当前任务、今日消耗、最近产出。

### 7.3 默认岗位模板库（内置，可改）

| 岗位 | 主要职责 | 关键禁止事项 | 交付物（DoD 示例） |
| --- | --- | --- | --- |
| **产品经理 PM** | 需求澄清、写 PRD、拆任务、定义验收标准 | 不写业务代码、不合并主干 | PRD.md + 任务拆解 + 验收清单（需人工门） |
| **架构师 Architect** | 技术方案、接口定义、依赖与风险评估 | 不直接改生产代码 | 技术方案.md + 接口定义（需人工门） |
| **UI/UX 设计** | 交互与视觉稿、设计规范 | 不改代码 | 设计说明 + 标注/切图产出 |
| **前端工程师 FE** | 界面与交互实现、自测 | 不改 DB schema、不动 CI、不合并主干 | 代码提交 + 构建通过 + 单测通过 |
| **后端工程师 BE** | 服务/接口/数据逻辑实现、自测 | 不改前端、不动 CI、不合并主干 | 代码提交 + 构建通过 + 接口自测记录 |
| **测试工程师 QA** | 用例设计、执行测试、提 bug、回归验证 | **不修代码**（保证独立性） | 测试用例 + 测试报告 + bug 工单（含复现步骤） |
| **代码审查 Reviewer** | 审查质量、安全、规范 | 不代替作者大改 | 审查意见 + 通过/打回结论 |
| **技术写作 TW** | 文档、README、变更日志 | 不改业务逻辑 | 文档提交 |
| **运维/发布 Ops** | 打包、部署脚本、环境检查 | **未经审批门不得真部署** | 发布清单 + 回滚方案（需人工门） |
| **数据分析 DA** | 数据清洗、指标、报告 | 不外发原始数据（必须过脱敏网关） | 分析报告 + 可复现脚本 |
| **研究/调研 RA** | 资料检索、竞品对比、摘要 | 不臆造来源，必须给链接 | 调研报告（每条结论带来源） |
| **秘书/助理 PA** | 日程、提醒、纪要、待办整理 | 不代我对外发消息（需审批） | 纪要/待办列表 |

> **岗位模板的设计原则**：每个岗位都要写清楚**禁止事项**。只写"能做什么"的岗位定义等于没有边界。

### 7.4 多 Agent 并行运行（本版新增）

**FR-G5 并发执行**：支持同时运行多个员工实例；默认并发上限可配（建议默认 3，按机器性能调整），超出则排队。
**FR-G6 资源隔离**：每个员工独立的工作目录、独立进程/工作线程、独立的工具调用配额；单个员工崩溃或被系统杀死不影响其他员工与哨兵层。
**FR-G7 状态隔离**：每个员工独立的会话上下文、任务队列、预算计数器、审计流。
**FR-G8 冲突预防（关键）**：
- 同一文件/目录默认**不允许两个员工同时写**（文件级锁 + 工作区隔离）。
- 代码类任务推荐 **git worktree / 独立分支**，由流程模板决定；合并主干必须过审批门。
- 冲突发生时不是"后写覆盖先写"，而是**明确报冲突并升级给人**。
**FR-G9 优先级与抢占**：哨兵层通知优先级高于员工普通任务；用户手动插入的任务可抢占排队任务。
**FR-G10 资源保护**：员工密集运行时不得让机器不可用（CPU/内存上限、可配置"工作时不许占满"策略、电池模式下自动降并发）。
**FR-G11 统一可见性**：一个视图能看到所有员工在干什么（当前任务、已运行时长、消耗、最后一步动作）。

### 7.5 任务看板与交接协议（M5 核心）

**FR-G12 任务看板（Kanban）**：状态集合固定为
`待办 → 就绪 → 进行中 → 待评审 → 待验证 → 已完成 / 已阻塞 / 已取消`
每张任务卡含：标题、描述、类型、负责人（员工）、提出人、依赖、交付物、验收标准、优先级、预算、历史时间线。

**FR-G13 交接协议（Handoff）**：员工之间**不通过自由对话**传递工作，而是通过结构化交接单：

```yaml
handoff:
  from: fe-01
  to: qa-01
  task_id: T-1042
  result: PASS            # PASS | FAIL | BLOCKED
  summary: "登录页响应式改造完成"
  artifacts:
    - path: "src/pages/login.tsx"
      commit: "a1b2c3d"
  verification:            # 必须是机械证据，不是自述
    - cmd: "pnpm build"
      exit_code: 0
    - cmd: "pnpm test -- login"
      exit_code: 0
      passed: 12
  known_issues: ["Safari 15 下圆角有 1px 偏差"]
  next_action: "请执行测试用例 TC-201 ~ TC-215"
```

**FR-G14 交接强制字段**：`result`、`artifacts`、`verification` 必填。**没有 verification 的交接单视为无效，不进入下一阶段。**
**FR-G15 返工回流**：QA 发现 bug 生成 bug 工单（含复现步骤、期望/实际、证据），自动路由回**原作者**（或流程指定的修复角色）；修复后必须回到 QA 标记回归通过，才能继续流转。
**FR-G16 循环与兜底（关键风控）**：
- 同一任务同一对角色之间的往返次数上限（默认 3 次），超限**强制升级给人**并附完整往返记录。
- 全局任务步数上限与时长上限；超限暂停并上报。
- 检测"无进展循环"（连续 N 次交接交付物无实质变化）→ 立即熔断。
**FR-G17 人的介入点**：用户可随时在看板任意卡片上暂停/改要求/重新指派/直接接管。

### 7.6 交付流程模板（Workflow Template）

用声明式 YAML 描述流水线，把用户描述的"PM → 前后端 → 测试 → 修 bug → 回归 → 产品验收"固化下来：

```yaml
name: feature-delivery
description: 从需求到验收的完整功能交付流程
stages:
  - id: prd
    role: product-manager
    output: [PRD.md, tasks.yaml]
    dod: [prd_has_acceptance_criteria]
    gate: human_approve          # PRD 定稿必须我确认
  - id: design
    role: architect
    depends_on: [prd]
    output: [tech-design.md, api-spec.yaml]
  - id: implement
    role: [frontend-engineer, backend-engineer]   # 并行
    depends_on: [design]
    parallel: true
    dod: [build_pass, unit_test_pass, lint_pass]
    on_success: qa
    on_failure: retry_self(max: 3)
  - id: qa
    role: qa-engineer
    depends_on: [implement]
    output: [test-report.md, bugs/*.yaml]
    on_bugs_found: route_to_author      # 按 bug 归属自动派回
    on_all_bugs_closed: regression
  - id: regression
    role: qa-engineer
    depends_on: [qa]
    dod: [all_bugs_verified_closed, full_test_pass]
    on_success: acceptance
    on_failure: route_to_author
  - id: acceptance
    role: product-manager
    depends_on: [regression]
    dod: [acceptance_checklist_pass]
    gate: human_approve          # 产品验收 = 我点头
escalation:
  on_max_retries: notify_human
  on_budget_exceeded: pause_and_notify
  on_blocked: notify_human
```

**FR-G18 流程模板能力**：阶段、依赖、并行、角色（可多角色并行）、DoD、失败处理策略、审批门、升级策略、超时。
**FR-G19 流程可视化**：界面能看到当前跑到哪个阶段、每个阶段的负责人、耗时、消耗、卡点。
**FR-G20 模板可创建/导入/导出**：内置若干模板（功能交付、bug 修复、文档撰写、调研报告、数据处理），支持自定义。
**FR-G21 阶段可跳过但需显式**：跳过必须有理由并留痕，禁止静默跳过验证阶段。

### 7.7 验证机制（对抗"假完成"，本版核心风控）

**FR-G22 机械验证优先**：DoD 必须是可执行、可复现的检查（构建、测试、lint、schema 校验、接口连通性、文件存在与格式、diff 范围检查）。
**FR-G23 禁止互相背书**：Agent 之间不允许用"我认为没问题"作为放行依据；任何"通过"结论必须附带可复现的命令与结果。
**FR-G24 独立验证角色**：关键流程中，**提出者与验证者必须是不同员工**（QA 不修代码，作者不自审）。
**FR-G25 抽查与一致性检查**：对员工声称的成果做抽样复核（如声称"测试通过"则实际重跑；声称"改了 3 个文件"则核对 diff）。
**FR-G26 未验证标记**：任何未通过机械验证的结论，在界面与报告中必须标注"未验证"，不得混入结论区。
**FR-G27 验证失败的处理**：验证失败不算"任务失败"，而是触发返工；连续失败升级给人并附失败证据。

### 7.8 预算与成本控制（本版新增）

**FR-G28 三级预算**：单任务 / 单员工单日 / 全系统单月。
**FR-G29 超限行为**：达到软阈值（如 80%）→ 通知；达到硬阈值 → **暂停任务并上报**，不静默继续。
**FR-G30 成本归因**：每次模型调用、每个任务、每个员工、每条流程都可查成本；月度报表可见"哪个员工最贵、哪些任务最烧钱"。
**FR-G31 降级策略**：接近预算时可自动降档到更便宜的模型或本地模型（必须**事前配置**，不得临时偷偷降级影响质量）。
**FR-G32 经济性熔断**：检测异常消耗（如某员工 token 增速异常）自动熔断并告警。

### 7.9 失败恢复与持久化（本版新增）

**FR-G33 任务不丢**：看板状态、任务上下文、执行进度持久化到 SQLite；进程重启后可恢复。
**FR-G34 幂等执行**：任务执行须能安全重试（对文件写入、git 操作、外部调用做幂等或补偿设计）。
**FR-G35 崩溃恢复**：员工崩溃后任务回到"就绪（被中断）"状态，可被重新领取，并保留中断前证据。
**FR-G36 停机会话恢复**：系统睡眠/重启后，进行中的任务标记为"待确认"，由用户或流程决定继续还是重跑（**不做"猜着继续"**）。
**FR-G37 完整时间线**：每个任务保留完整时间线（谁在什么时候做了什么、用了什么工具、结果如何），可回放。

### 7.10 多团队与跨团队协作（M6，本版新增）

#### 7.10.1 组织模型：我 → 多个团队 → 团队成员

```
                       我（老板 / 唯一决策者）
        ┌───────────────┼───────────────┐
   团队 A（项目 A）   团队 B（项目 B）   团队 C（项目 C）
   ├ PM               ├ 研究            ├ 数据分析
   ├ 前端 ×2          ├ 技术写作        ├ PRD 交付
   ├ 后端             └ 审查            └ 报告交付
   ├ QA
   └ 流程/预算/工作区
        │ 跨团队接口 ▲          │ 跨团队接口
        └────────────┴──────────┘
        （显式契约 + SLA + 预算归属 + 审计）
```

**层级顺序（关键）**：**先有"一个团队能完整交付"，再有"多个团队互不干扰"，最后才有"团队之间协作"。** 顺序颠倒会同时得到三种失控：员工打架、项目串味、预算黑箱。

**FR-G43 团队是一个项目单元，不是文件夹**：每个团队必须显式声明以下要素（缺一不可）：

| 要素 | 说明 | 示例 |
| --- | --- | --- |
| **所属项目** | 这个团队为哪个项目负责 | "个人博客重构" |
| **目标（Objective）** | 团队的交付目标与完成定义 | "上线新版博客，含评论功能" |
| **成员（Members）** | 员工列表与各自岗位 | PM ×1、前端 ×2、后端 ×1、QA ×1 |
| **流程模板** | 该团队的交付流程 | feature-delivery |
| **工作区与资料库** | 项目代码目录、文档目录、知识源 | `~/projects/blog` |
| **预算** | 团队级成本上限 | $20/月 |
| **对外接口** | 能对外提供/需要外部提供什么 | 见 7.10.3 |
| **负责人（Owner）** | 默认是我；可指定某个员工做协调人（不对等人类权威） | 我 |

**FR-G44 团队可创建/复制/归档**：从团队模板一键实例化；可复制现有团队（新项目复用同一套配置）；项目结束后归档（保留交付物与时间线，停止消耗）。
**FR-G45 团队数量不设产品上限**：但受全局资源上限约束（见 7.10.6）。
**FR-G46 项目隔离**：每个团队独立工作区、独立看板、独立预算账户、独立资料库索引；**默认不共享上下文与记忆**。

#### 7.10.2 团队模板与跨团队员工归属

**FR-G47 团队模板（Team Template）**：模板 = 岗位集合（Roles）+ 流程模板（Workflow）+ 对外接口约定（Interfaces）+ 默认预算。用户可一键创建"一个新项目团队"，填项目名与工作区即可开工。

```yaml
name: software-project-team
description: 标准软件项目团队
roles:
  - product-manager: 1
  - architect: 1
  - frontend-engineer: 2
  - backend-engineer: 1
  - qa-engineer: 1
workflow: feature-delivery
interfaces:
  provides:
    - id: feature-delivery-api
      input: 需求描述
      output: 可运行的功能 + 测试报告
  needs:
    - id: design-assets        # 需要设计团队提供
      from_team: design
budget: { monthly: 20, per_task: 1.5 }
```

**FR-G48 模板可创建/导入/导出**；内置模板建议：软件项目团队 / Bug 修复小队 / 数据分析团队 / 内容创作团队 / 调研团队。
**FR-G49 员工的主团队与借用（关键约束）**：
- 每个员工有且仅有一个**主团队（Owner Team）**：默认的工作归属与预算账户。
- 员工可被其他团队**借用**，但必须是**显式的共享资源授权**（FR-G55），并写明：借给谁、用多久、时间占比上限、预算算谁的。
- **默认不允许一个员工同时属于多个团队**（避免优先级内战，见 R21）。
- 界面必须能一眼看到"这个员工当前在给哪个团队干活、时间怎么分配"。
**FR-G50 共享员工（Shared Resource）**：支持将某员工标记为跨团队共享（如"架构师"被所有团队共用），规则：
- 必须设**并发上限**（同一时刻只能服务一个团队）与**时间配额**（如每周 ≤ 10 小时）。
- 共享员工的消耗按**实际服务对象**记账，不混算。
- 共享员工被争抢时按优先级排队，冲突升级给我。

#### 7.10.3 跨团队接口契约（Team Interface）

**FR-G51 团队之间只能通过显式接口协作**：接口是跨团队协作的**唯一通道**，禁止员工直接去读另一个团队的工作区或看板。

```yaml
interface:
  id: ui-component-delivery
  provider_team: design-team
  consumer_team: blog-team
  version: 1.2.0
  input:
    description: "需求与页面清单"
    schema: { pages: "string[]", style_guide: "url" }
  output:
    description: "设计稿 + 标注 + 切图"
    schema: { figma_url: "url", assets: "path[]" }
  acceptance: ["所有页面有标注", "切图导出 2x/3x"]
  sla: { respond_within: 4h, deliver_within: 3d }
  cost_bearer: consumer        # provider | consumer | split
```

**FR-G52 接口必须声明**：输入/输出 schema、验收标准、响应时限（SLA）、成本承担方、版本号、负责人。
**FR-G53 接口变更留痕**：变更接口必须双方团队确认（可由团队负责人员工代办，但**破坏性变更需我审批**）；旧版本保留，调用方未迁移前不得强推。
**FR-G54 契约测试（建议）**：接口交付物在跨团队交接时先做**机械校验**（schema 校验 / 文件存在与格式 / 验收标准逐条检查），不合格直接打回，不进入人工视野。

#### 7.10.4 跨团队协作的三种模式

| 模式 | 场景 | 机制 | 审批要求 |
| --- | --- | --- | --- |
| **服务式（Service）** | A 团队有 B 团队需要的稳定能力（如设计、法务、翻译） | B 通过接口调用 A；A 建任务、按 SLA 交付 | 无需逐次审批（接口已授权） |
| **联合项目（Joint Project）** | 两个团队共同负责一个项目 | 建**联合看板**，明确 RACI（谁负责/谁批准/咨询谁/告知谁），指定牵头团队 | 立项时我确认 RACI |
| **人力借用（Secondment）** | 临时把 A 的专家借给 B 用一段时间 | 限时、限配额；消耗按调用方团队记账 | 有时限与配额上限，超限需我批准 |

**FR-G55 跨团队交接（Cross-Team Handoff）**：在普通交接单基础上必须额外包含：

| 字段 | 说明 |
| --- | --- |
| `from_team` / `to_team` | 团队归属（跨团队路由的依据） |
| `interface_id` | 依据哪个接口契约 |
| `sla_deadline` | 响应/交付截止时间 |
| `cost_bearer` | 本次消耗算谁的预算 |
| `contract_check` | 契约测试结果（机械校验证据） |
| `escalation_path` | 超时后升级给谁（超时自动催办，二次超时通知我） |

**FR-G56 跨团队协作的四条铁律**：
1. **接口是唯一通道**：跨团队不共享上下文、不共享工作区、不共享凭据。
2. **跨团队数据默认禁止**：确需访问必须显式授权（时限 + 范围 + 审计），且仍然**必须过脱敏网关**。
3. **预算归属必须明确**：不允许"两家都以为是对方付钱"（见 R22）。
4. **冲突不自动抢占**：共享资源被争抢时，**升级给我**，绝不自动抢。

#### 7.10.5 团队级审批门与责任

**FR-G57 团队级审批门**：每个团队可独立配置审批门（如团队 A 要求"合并主干必须我批准"，团队 B 允许"自动合并且仅通知"）。
**FR-G58 团队负责人（可选）**：可指定某个员工担任团队协调人（做排期、催办、对外接口沟通），但**它不具备人类的批准权威** —— 审批门永远指向我。
**FR-G59 团队级 SLA 与绩效**：按团队统计交付达成率、返工率、跨团队等待时长、成本。
**FR-G60 团队级归档与清算**：归档时输出团队总结（交付了什么、花了多少、遗留什么、接口契约最终版本）。

#### 7.10.6 多团队组织与并发控制

**FR-G61 三层并发上限**：全局并发 ≤ N（默认 3，可调）· 单团队并发 ≤ M（默认 2）· 单员工同时只做一件事。
**FR-G62 全局资源仲裁**：所有团队共享机器资源；超出上限的任务**排队而非失败**；排队对用户可见（哪个团队在等、等什么）。
**FR-G63 团队优先级**：可为团队设优先级（如"客户项目 > 个人实验"）；高优先级团队可优先占用并发额度，但**不得饿死**低优先级团队（设最大连续占用时长，防止一个团队长期霸占）。
**FR-G64 团队预算账户**：团队级预算独立核算；团队预算耗尽时**该团队暂停**，不影响其他团队；超限通知我并给出"追加预算 / 缩减范围 / 暂停项目"的选项。
**FR-G65 跨团队预算归集**：全局月度报表能按团队、按接口、按跨团队调用分别归集成本，回答"这个月哪个项目最贵、跨团队协作花了多少"。

#### 7.10.7 团队隔离（在员工隔离之上再加一层）

**FR-G66 团队级隔离**：团队工作区、看板、资料库、凭据作用域、预算账户全部隔离；跨团队读取默认禁止。
**FR-G67 跨团队共享的内容仅限三类**：① 显式接口的输入/输出交付物 ② 显式的消息 ③ 显式授权的共享知识条目。**不共享**上下文、记忆、工作区、凭据。
**FR-G68 越界检测**：任何试图访问其他团队工作区/凭据的行为，引擎层拒绝并记录审计 + 通知我（这可能是提示词被污染的信号）。

#### 7.10.8 组织全景视图

**FR-G69 一屏看全部团队**：每个团队一张卡片 —— 目标、成员、当前在跑什么、预算消耗、阻塞项、跨团队依赖。
**FR-G70 跨团队依赖图**：谁在等谁、等了多久、SLA 是否超时；瓶颈一眼可见。
**FR-G71 组织级通知路由**：不同团队的通知可按团队分流（如客户项目 → 手机推送 + 声音；个人实验 → 静默进摘要）。
**FR-G72 跨团队审计检索**：按团队、按接口、按时间检索跨团队的全部交互与外发记录。

### 7.11 员工数据隔离（M4–M5）

**FR-G38 工作区隔离**：员工只能读写自己工作区 + 被显式授权的目录；跨员工读取默认禁止。
**FR-G39 凭据作用域**：每个员工绑定独立的凭据作用域（如市场员工的 CRM 凭据 ≠ 开发员工的 git 凭据）。
**FR-G40 数据传递受控**：员工间传递的内容必须走看板交付物或消息总线，且**同样经过脱敏网关**（禁止"开发员工把客户数据原文塞给市场员工"）。
**FR-G41 跨域访问需显式授权**：确需跨员工数据时，由用户在授权界面显式开启，并留下时限与审计记录。
**FR-G42 审计可查**：支持按员工、按任务、按时间检索"谁访问了什么、外发了什么"。

### 7.12 知识库与 RAG 检索（M3–M7，本版新增）

#### 7.12.1 目标：让"知道"取代"猜"

**FR-G77 要解决的问题**：模型不知道我的项目、我的文档、我的历史决策，于是它就编。知识库的作用是**把"该知道的事"在需要的时候喂到它面前**，从而：提高回答与做事的准确性（基于事实而非先验）；降低幻觉（**有据可依 + 无据可查时必须承认不知道**）；减少重复解释（我不用每次把背景再讲一遍）；让员工之间、团队之间、跨会话之间传递稳定知识，而不是靠"记忆"丢三落四。

**FR-G78 定位**：RAG 是**准确性的基础设施**，不是聊天加分项。它必须服务于三件事：**判断**（这封邮件重要吗）、**生成**（写 PRD / 写代码）、**验证**（这条结论有依据吗）。

#### 7.12.2 知识分层与数据分级（关键约束）

**FR-G79 知识层级**：知识库必须分层，且层级与作用域绑定：

| 层级 | 内容 | 可见范围 | 默认数据分级 |
| --- | --- | --- | --- |
| **个人知识** | 我的笔记、邮件、日程、随手记录 | 仅我 + 我明确授权的员工 | 多为 L2 |
| **团队/项目知识** | 该项目需求文档、接口文档、代码库、会议纪要 | 仅本团队成员 | L1–L2 |
| **组织共享知识** | 通用规范、编码标准、常用流程、模板 | 所有团队 | L0–L1 |
| **外部知识** | 公开文档、网页、第三方资料 | 所有人 | L0 |

**FR-G80 每条知识必须带分级标签**：沿用 §8.1 的 L0–L3，**默认保守（未知→L2）**；分级标签不可被员工或自学习下调。
**FR-G81 检索即受控（铁律）**：**知识检索同样受数据分级与团队隔离约束** —— 员工只能检索到自己有权访问的知识（团队知识不跨团队、L2/L3 不越权）。
**FR-G82 检索结果外发同样过脱敏网关（铁律）**：从知识库检索出来的片段在送给模型之前**必须过网关**，不能因为"这是我自己库里的东西"就免除脱敏。
**FR-G83 向量同样被视为数据（易被忽视）**：embedding 可被部分还原，因此**向量默认不出机器**；使用云端 embedding 需显式授权，并按 L2 处理。

#### 7.12.3 数据源与摄取管道

**FR-G84 支持的数据源（按里程碑逐步放开）**：本地文档（Markdown / PDF / DOCX / TXT / 代码）、项目代码库、网页与 RSS、邮件与消息、日历与会议纪要、我的手工笔记、员工产出的交付物（PRD、测试报告、复盘）。
**FR-G85 摄取管道**：`采集 → 解析（保留结构：标题/表格/代码块/页码）→ 清洗 → 分块 → 打标签（分级/团队/来源/时间/作者）→ 脱敏预处理 → 嵌入 → 入库 → 建立关键词索引（BM25）+ 向量索引（ANN）`
**FR-G86 分块策略**：按结构优先（标题层级、段落、函数边界）而非固定字数切；带重叠避免切断语义；表格与代码块**整体保留不切**；每块记录来源位置（文件 + 行号/页码）以便引用可回溯。
**FR-G87 增量更新**：以内容哈希判断变更，只重建变化的块；支持"软删除 + 保留历史版本"，避免知识被静默改写。
**FR-G88 摄取前脱敏**：入库前即对 L2/L3 内容做本地脱敏（或标记"禁止嵌入外部模型"），**不要把敏感原文先灌进库再说**。
**FR-G89 时间与新鲜度**：每条知识记录 `有效时间 / 更新时间 / 是否已过期`；回答时优先新知识，冲突时提示"存在新旧两个版本"。

#### 7.12.4 检索策略

**FR-G90 混合检索（默认）**：向量检索（语义）+ BM25（关键词/专有名词/代码标识符）双路召回，再**重排（rerank）**取 Top-K。纯向量检索在代码与专有名词上表现差，必须混合。
**FR-G91 元数据过滤优先于语义相似**：先按团队、分级、时间、来源过滤，再做相似度排序 —— **防止"语义很像但无权看"的内容混入**。
**FR-G92 查询改写**：员工口语化的需求先改写成检索友好的查询（拆关键词、补同义词、去噪），并支持多轮检索（先查概念再查细节）。
**FR-G93 引用与可溯源（对抗幻觉的核心）**：每条入库知识保留 `来源文件 + 位置 + 更新时间 + 内容哈希`；**所有基于知识库的结论必须给出可点击引用**。
**FR-G94 证据不足必须承认（铁律）**：

> 当检索结果为空、或相关度低于阈值时，员工**必须明确说"知识库里没有找到依据"**，并给出选项（扩展检索范围 / 用外部检索 / 让我提供资料 / 标注为推测）。
> **严禁在无依据时编造细节**（尤其是数字、日期、人名、接口名、法条、引用）。未验证内容必须带"未验证"标记（对应 §7.7 FR-G26）。

**FR-G95 与验证机制联动**：涉及内部知识关键的结论，必须通过"引用可解析 + 原文可核对"的机械校验才能进入结论区；引用失效（文件已删/已改）自动降级为"引用已失效"。

#### 7.12.5 知识冲突与治理

**FR-G96 冲突检测**：同一主题出现互相矛盾的内容时（如两版接口文档），系统检测并提示，**不由模型自行选择**。
**FR-G97 冲突处理规则**：① 优先新版本 ② 优先权威来源（正式文档 > 聊天记录 > 员工推测）③ 仍冲突则**上报给我裁决**，并把裁决结果写回知识库（形成稳定的组织记忆）。
**FR-G98 知识来源可信度分级**：正式交付物 > 我的手工笔记 > 外部公开资料 > 员工生成内容（**员工产出默认标记为"待确认"，不得直接当作事实依据**）。
**FR-G99 污染防护（重要）**：员工自己写的东西若无差别入库，会形成"自己引用自己"的幻觉放大回路。因此员工产出入库必须带 `generated_by=employee` 标签，检索时**降权**，且不能作为唯一依据。

#### 7.12.6 复杂度与成本

**FR-G100 两级检索**：默认只用本地索引（零成本、快）；仅在本地检索证据不足时才走外部检索（网络/大模型辅助），并记录原因。
**FR-G101 缓存**：高频查询结果缓存（含失效时间），避免重复嵌入与重复检索烧钱。
**FR-G102 库容量与性能**：单库支持 ≥ 10 万块；检索 P95 < 500 ms（本地）；索引重建不阻塞主流程。
**FR-G103 索引可重建 / 可迁移**：索引文件可删除重建（**原文是唯一真相源**）；导出时包含原文与元数据，不依赖不可解释的二进制索引。

### 7.13 上下文管理与自动压缩（M4–M7，本版新增）

#### 7.13.1 为什么必须做

**FR-G104 问题**：员工干的活比聊天长得多 —— 一条"PRD → 开发 → 测试 → 回归"的链路会累积大量工具输出、文件内容、失败日志与往返记录。上下文必然超限，而**简单截断会丢关键决策**，模型随即开始编（这是幻觉的另一个主要来源）。

**FR-G105 目标**：在**不丢关键事实**的前提下把上下文压到窗口内，并且**压缩过程本身可审计、可回溯、可还原**。

#### 7.13.2 分层上下文模型

**FR-G106 四层结构**：

| 层 | 内容 | 压缩策略 |
| --- | --- | --- |
| **锚定层（不可压缩）** | 任务目标、验收标准（DoD）、硬约束与禁止事项、已批准的决策、接口契约 | **逐字保留**，永不摘要 |
| **受保护事实层（不可有损压缩）** | 关键数字、文件路径、提交号、接口名、报错原文、人名日期、金额 | **逐字保留**（可去重、可折叠，但不可改写） |
| **工作层（可压缩）** | 当前步骤的推理与工具输出、近期往返记录 | 摘要化 / 结构化提取（滑动窗口保留最近 N 轮原文） |
| **历史层（移出上下文）** | 早期阶段过程、已完成的子任务明细、旧搜索结果 | **移出到知识库/快照，按需检索拉回**（与 §7.12 联动） |

> **原则：能检索的就不留在上下文里。** 上下文只放"现在必须知道的"，历史一律可检索。

#### 7.13.3 压缩触发与算法

**FR-G107 触发条件**：上下文使用率达到阈值（默认 70% 预警、85% 自动压缩）+ 阶段性边界（一个阶段完成、一次交接发生）+ 手动触发。
**FR-G108 压缩时机**：只在**安全断点**压缩（一轮工具调用结束后、阶段交界处），**绝不在一半操作里压缩**（否则丢失中间状态）。
**FR-G109 压缩步骤**：① 冻结锚定层与受保护事实层（挑出来原样保留）；② 对工作层做结构化摘要（保留：做了什么、结论、失败原因、下一步；丢弃：试错细节、重复输出、完整日志）；③ 把历史层写成**可检索快照**（带引用）并移出活跃上下文；④ 重新组装并**重新校验**（锚定层哈希比对，确保一个字没变）。
**FR-G110 工具输出的压缩规则**：大输出（构建日志、测试报告、文件内容）只保留**结论 + 关键片段 + 指针**（指向完整产物文件），绝不整段塞进上下文。
**FR-G111 压缩摘要本身也是知识**：压缩产生的阶段摘要入库（标 `kind=summary`），后续可被检索 —— **这是"长任务不丢记忆"的实现方式**。
**FR-G112 无损兜底**：压缩前的完整上下文必须落盘为快照（可回滚、可人工查看、可对比），保留期可配（默认 7 天）。

#### 7.13.4 防止"压缩导致幻觉"（关键风控）

**FR-G113 三条铁律**：① **摘要不得引入原文没有的信息**（不允许"合理推测"式补全）；② **不确定的内容必须显式标注**（如"该结论基于已被压缩的早期讨论，未复核"）；③ **锚定层与受保护事实层不可被摘要替代** —— 宁可挤窗口，也不改写约束与数字。
**FR-G114 压缩后自检**：压缩完成后做一致性检查（关键实体是否仍存在、DoD 是否仍完整、未决问题是否仍被标记），不通过则回滚重压。
**FR-G115 压缩透明**：我可以在界面看到"这个任务的上下文被压缩了几次、每次丢了什么、摘要是什么"，并可恢复到任一快照。

#### 7.13.5 与预算、并发的联动

**FR-G116 token 预算**：每个员工/任务有上下文 token 上限（属于 §7.8 预算的一部分）；压缩次数与成本计入成本归因。
**FR-G117 压缩的成本控制（v0.6 修订）**：压缩本身必须调用模型（无本地模型可用，见技术架构 §5.1），是纯增量成本。因此三条替代优化：① **源头减量优先**（工具输出进上下文前先裁剪，只留结论 + 关键片段 + 指针）② 压缩固定用**最便宜的可用模型档** ③ 阶段摘要**缓存复用**，避免重复压缩同一段内容。压缩失败时**保留原文并告警**，绝不因压缩失败而丢内容。
**FR-G118 跨员工/跨团队的上下文传递**：交接时**不传原始上下文**，只传结构化交接单（§7.5）与必要的知识引用 —— 这是控制上下文膨胀的根本手段。

### 7.14 软件能力与安装治理（M4–M6，本版新增）

#### 7.14.1 能力升级与一条铁律

> 员工不只是"会写代码的 Agent"，而是**能操作我这台电脑上已有软件的数字同事**。
> 遇到自己解决不了的问题，它应该用软件去解决；如果软件不够，它应该**向我申请**。

这条需求把员工的能力来源从"自己的推理与代码"扩展到"整台电脑的软件生态"，价值很大，但同时打开了一个巨大的风险面。因此配一条铁律：

> ## ⚠️ 铁律：**能力的扩张永远不是自动的。**
> 员工可以自动**调用**已被授权的软件；但**装什么、拿到什么权限、数据发往哪里，任何一项扩张都必须我点头。**

**FR-G119 双向治理模型**：软件能力沿两个维度分级治理，两个维度独立评估、取更严的一侧：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| **调用方式** | ① API / CLI / 脚本接口 ② 应用内自动化（AppleScript、VBA、插件 API） ③ GUI 自动化（模拟点击、键鼠、无障碍接口、截图识别） | 越靠右越脆弱、越危险 |
| **安装位置** | ① 我的机器（本地） ② 员工沙箱环境 ③ 云端 | 越靠右越不影响我的机器 |

#### 7.14.2 软件准入分级与黑名单

**FR-G120 四级准入**：

| 级别 | 例子 | 策略 |
| --- | --- | --- |
| **A 完全自动** | 只读或低风险 CLI：`git status`、`ls`、`pdftotext`、`jq`、`ffmpeg` 转码 | 授权后自动调用，仅记审计 |
| **B 自动 + 审计** | 有写入或对外副作用的调用：Office 文档生成、Excel 数据处理、浏览器开页面、包管理器安装依赖、发邮件 | 授权后自动，但每次留痕，可随时撤销 |
| **C 需审批** | **安装任何新软件**（含应用内扩展/插件）、安装需要管理员权限、会花钱、会对外发布内容、批量改动 | 逐次申请，我批准 |
| **D 永不允许** | 见黑名单 | 引擎层直接拒绝，连申请通道都不开放 |

**FR-G121 黑名单（默认内置，不可被员工或自学习放开）**：

- 权限提升：`sudo` 全局放行、修改系统完整性保护（SIP）、改内核扩展、装系统级证书、改防火墙
- 系统关键：磁盘工具、系统更新、用户与权限管理、Time Machine 配置
- 安全与凭据：钥匙串访问工具、密码管理器、企业 VPN/零信任客户端
- 数据外泄风险：网盘/同步客户端的未授权登录、远程控制类软件（TeamViewer 等）、匿名代理/VPN 配置
- 无来源签名的可执行文件：**任何形式的"下载一个 .dmg/.exe 直接跑"一律拒绝**
- 我不允许的通信类软件（避免它代我对外发言）

**FR-G122 黑名单之外还需「来源白名单」**：即使不在黑名单，也只能从白名单来源获取（Homebrew 及国内镜像、官方开发者签名分发包、App Store、我指定的内部源）。**来源比软件名更重要。**
**FR-G123 应用内安装同等对待**：VS Code 扩展、npm/pip 包、浏览器扩展、插件市场安装 —— 虽然不需要管理员权限，但**同样引入可执行代码**，一律走 C 级审批 + 来源白名单。策略是"低摩擦但不失监管"：同类可预授权（如"允许该员工安装 GitHub 官方来源的 VS Code 扩展"）。

#### 7.14.3 软件能力清单（Capability Manifest）

**FR-G124 调用前必须先登记**：任何软件在被员工调用前，必须由系统（或由员工提议、我确认）登记以下信息：

| 字段 | 说明 |
| --- | --- |
| 名称 / 版本 / 路径 | 精确定位到可执行入口 |
| 它能做什么（能力描述） | 供员工检索："我需要把 Markdown 转 PDF，谁行？" |
| 调用方式 | CLI 命令模板 / AppleScript / GUI 步骤，**优先选最稳定的一档** |
| 入参出参格式 | 让员工知道怎么喂数据、怎么读结果 |
| 权限需求 | 需要读哪些目录、是否需要网络、是否需要管理员权限 |
| **数据去向** | 它会不会把数据传到外部（云服务类软件尤其重要） |
| 沙箱可行性 | 能否在员工沙箱里跑 |
| 已知坑 | 历史失败原因（如"某版本无头模式崩溃"） |

**FR-G125 能力检索**：员工遇到任务时先查能力清单，避免重复试错、避免重复申请同一软件。
**FR-G126 首选最稳定路径**：同一目标优先 API/CLI，不优先 GUI 自动化（理由见 R27）。
**FR-G127 调用失败降级链**：`GUI 自动化` → 失败 → `AppleScript/应用自动化` → 失败 → `CLI/API` → 失败 → **生成操作引导请我手动执行**（见 7.14.7）；同一软件连续失败 3 次自动标记"不推荐"并上报。

#### 7.14.4 软件申请流程

**FR-G128 申请单（SoftwareRequest）**必须包含：

```yaml
request_id: SR-0087
requested_by: da-01            # 发起员工
team: analytics-team
software:
  name: "pandoc"
  purpose: "把 Markdown 报告转成 Word/PDF 交付给客户"
  why_existing_fail: "现有工具只能输出 txt，无法保留表格与样式"
  alternatives_considered: ["LibreOffice CLI（试用后中文排版错乱）"]
install:
  method: brew                 # brew | pkg | app_store | manual
  source: "中科大镜像 / homebrew-core"
  version: "3.1.11"            # 锁定版本，不用 latest
  requires_admin: false
  size: "180 MB"
  license: "GPL-2.0（免费开源）"
  permissions: ["read:/Users/me/reports", "write:/tmp"]
  data_egress: "无（纯本地转换）"
  sandbox_ok: true
```

**FR-G129 申请前预检**：① 能力清单里是否已有能干的 ② 是否命中黑名单 ③ 信息是否完整（缺 `data_egress` 或 `license` 直接驳回）。预检失败**不给员工打扰我的机会**，直接回绝并说明原因。
**FR-G130 风险评级与审批**：按"是否需管理员权限 / 是否联网外发 / 是否开源免费 / 来源可信度"分成低中高三档 → 通知我（含一页风险摘要）→ 我可批准 / 拒绝 / 改条件（如"装可以，但必须在沙箱里跑"）。
**FR-G131 高危项必须人工执行**：需要管理员权限、驱动、内核扩展、系统级配置的安装，**系统只生成指引，绝不自动执行**。
**FR-G132 安装到沙箱优先**：能在员工沙箱环境（独立目录 / 虚拟环境 / 容器）里运行的，一律装沙箱，不污染我的机器主环境。
**FR-G133 安装后验证**：装完必须做机械验证（可执行文件存在 + 版本匹配 + 一个最小冒烟用例通过），失败自动回滚并报告。
**FR-G134 试用期与转正**：新软件默认 14 天试用期，期间记录调用次数与失败率；到期时我给结论（保留 / 卸载 / 转正为常用工具），不自动延期。
**FR-G135 采购与付费边界**：付费软件的购买与许可证**由我完成**，系统只负责生成申请报告并登记许可证信息，**不代付、不代填支付信息**。
**FR-G136 卸载与残留清理**：卸载时清理安装目录、临时数据、启动项，保留申请记录与调用历史，验证无残留。

#### 7.14.5 软件调用的安全约束

**FR-G137 软件调用记录**：每次调用记录员工、软件与版本、命令/动作、参数摘要、耗时、退出码、产物路径。
**FR-G138 软件输出同样过脱敏网关（关键）**：软件读到/输出的数据仍是数据，**不能因为"是本地软件"就绕过脱敏**。例：员工用邮件客户端读邮件后要交给模型，仍须过网关。
**FR-G139 截图与 GUI 自动化涉及的数据**：GUI 自动化常伴随截屏，而**图片无法可靠脱敏** →

- 默认**禁止把屏幕内容发往任何外部模型**，需要时逐次人工确认；
- 能用"读控件文本"解决的，不允许用截图；
- 屏幕内容只在本地用于识别与操作，用完即删。

**FR-G140 软件与账户凭据隔离**：员工调用软件时使用**为它分配的凭据**（而非我本人的登录态），避免通过自动化"复用我的账号"绕过权限；确需使用我的登录态时，必须显式授权并留下调用记录。

#### 7.14.6 并发与资源

**FR-G141 软件级锁**：同一软件实例可能不支持并发（如 GUI 应用、Office、数据库客户端）→ 加软件级锁与调用队列，排队而不是并发乱调。
**FR-G142 超时与残留处理**：所有调用设超时；异常退出后清理残留进程与临时文件（避免僵尸进程占资源）。
**FR-G143 跨软件编排**：允许员工把多个软件串成一条流水线（如"浏览器查资料 → Excel 整理 → Keynote 出稿"），但整条链作为一个任务记录，中间产物保留，失败可从中断点续跑。

#### 7.14.7 手动兜底：操作引导

**FR-G144 当自动化不可靠或不值得做时**：员工输出标准化的**手动操作引导**而非硬编：

```yaml
manual_guide:
  task: T-2051
  reason: "该软件的安装需要管理员权限，按策略必须由你执行"
  steps:
    - "打开「系统设置 → 隐私与安全性」"
    - "点击「仍要打开」，输入密码"
    - "回到本应用点击「已完成」"
  expected_result: "员工状态变为「环境就绪」，任务自动继续"
  fallback: "如失败，员工会改用 LibreOffice CLI 路线"
```

我完成后点「已完成」，任务自动继续（**人机接力**，而不是让员工瞎试）。

#### 7.14.8 软件治理面板

**FR-G145 一屏管理软件能力**：已登记软件与版本、每员工可用范围、调用次数与失败率、申请记录（待批/已批/已拒/试用中）、黑名单与来源白名单、许可证登记。
**FR-G146 定期体检**：检查软件更新（**只报告不自动升级** —— 自动升级会破坏已调通的自动化）、检查许可证到期、检查长期未使用的软件并建议卸载。

### 7.15 编排架构取向

**FR-G73 架构取向（建议）**：**中央编排器 + 独立员工进程 + 看板与消息总线**，编排器内部再分两级（组织级 / 团队级）。

| 角色 | 职责 |
| --- | --- |
| **组织编排器（Org Orchestrator）** | 团队注册与生命周期、跨团队接口与路由、三层并发仲裁、团队预算核算、跨团队 SLA 与升级、组织全景 |
| **团队编排器（Team Orchestrator）** | 该团队的看板真相、流程模板、依赖与路由、成员与调度、失败恢复、团队预算 |
| 员工进程（Worker） | 单个员工的一次执行；无状态化设计，上下文从存储加载；崩溃不影响他人 |
| 消息/事件总线 | 交接单（含跨团队）、状态变更、通知、审计事件 |
| 共享内核 | 脱敏网关、凭据、审计、日志、模型 Provider、**知识库与检索**、**上下文压缩器** |

**FR-G74 两级编排的边界**：团队内部的事**不惊动**组织级；只有跨团队接口调用、共享资源争抢、预算触顶、破坏性接口变更才上升。
**FR-G75 组织记忆隔离**：团队级记忆默认不互通；组织级只保留"跨团队接口的契约与历史"这一层公共记忆。

**为什么不采用"多 Agent 自由对话"**：自由对话式协同无法保证可追溯、可复现、可熔断，成本与循环风险不可控。**用显式看板 + 结构化交接取代对话式协作；团队之间再用显式接口契约取代自由协作。**

**FR-G76 与标准协议的关系**：内部协作使用自有结构化协议（简单、可控、可审计）；对外集成采用 **MCP 作为工具接入**、**A2A 作为外部 Agent / 外部团队接入**（列为 M8+ 可能项，见开放问题 Q6）。

## 8. 数据安全与脱敏（M0 核心，本版新增）

### 8.1 数据分级

| 级别 | 定义 | 外发策略 |
| --- | --- | --- |
| **L0 公开** | 已公开的文档、开源代码、公开网页 | 可直接外发 |
| **L1 内部** | 工作内容、代码、内部文档、非个人化数据 | **字段级脱敏**后可外发 |
| **L2 敏感** | 个人身份信息、客户资料、合同、财务、健康 | **强制脱敏**，默认倾向本地模型；外发需显式允许 |
| **L3 机密** | 凭据、私钥、密码、Token、密钥文件 | **永不出机器**，本地模型也隔离；仅本地密钥库可读 |

**FR-S1 默认保守**：无法判定级别的数据一律按 **L2** 处理。
**FR-S2 分级来源**：① 数据源声明的默认级别（如邮件=L2、公开 RSS=L0）② 内容检测升级（如正文里发现身份证号则整段升级）③ 用户手动标注。
**FR-S3 级别只升不降（自动）**：自动化只能提升级别；降低级别必须人工确认。

### 8.2 脱敏外发网关（所有外发请求的唯一出口）

**FR-S4 唯一出口**：任何发往外部模型的请求必须经过网关；**不存在绕过路径**（引擎层强制，非约定）。
**FR-S5 网关处理流程**：

```
入站载荷 → 判定级别 → 检测敏感项 → 脱敏/替换占位符 → 记录审计 → 外发
                                                              ↓
交付给用户/员工 ← 本地还原真实值 ← 接收响应 ←────────────────────┘
```

**FR-S6 可逆占位符（关键设计）**：检测到的敏感值替换为**会话内稳定**的占位符（`[EMAIL_1]`、`[PHONE_2]`、`[ID_3]`），本地保存映射表；模型返回后自动还原。

- 好处：模型看不到真实值，但输出仍可直接使用（"把回复发给 [EMAIL_1]"→ 还原为真实地址）。
- 约束：映射表只存本地、内存优先、不写日志；会话结束或超时后清除。

**FR-S7 检测器清单（v1）**：中国大陆身份证、手机号、银行卡、邮箱、详细地址、IP、API Key/Token、私钥块、数据库连接串、护照号、车牌、自定义关键词与正则（用户可加）。
**FR-S8 检测策略**：正则 + 校验位（如身份证/银行卡校验） + 上下文启发式（如"身份证"关键词附近）；宁可过脱敏，不可漏脱敏。
**FR-S9 脱敏强度可配**：按级别配置替换 / 掩码（`138****1234`）/ 删除 / 泛化（"某市某区"）。
**FR-S10 审计记录**：每次出站记录时间、发起员工、目标 Provider/模型、载荷分级、命中的检测器、脱敏项数量与类型（**不记录原文**）、策略版本、请求哈希、响应状态。
**FR-S11 异常拦截**：检测器命中 L3 或脱敏失败时 **fail-closed**：直接阻断请求并告知用户，不允许"降级放行"。
**FR-S12 出站预览**：用户可在设置中查看"最近 N 次外发的脱敏后内容"，确认没有不该发的东西；支持一键阻断某类外发。
**FR-S13 敏感数据路由策略（v0.6 修订）**：L2 数据**不默认外发**；若未配置可处理 L2 的本地模型，则：优先尝试脱敏后降级为 L1 再外发（需策略允许）；若脱敏后仍属敏感，**拒答并说明原因**（fail-closed），并给出选项：仅本地处理（若已配置本地模型）/ 我手动提供可外发版本 / 放弃该步骤。**严禁"提示一下然后照发"**。配置了本地模型时，L2 默认路由到本地模型。
**FR-S14 多模态脱敏（M3 之后）**：图片/截图中的人脸、证件、屏幕内容需专门处理；在实现之前，**含图像的外发一律阻断或要求人工确认**。
**FR-S15 内容长度与上下文控制**：网关同时限制单次外发的字符量与上下文范围，避免"为了让模型理解，把整个文件都发出去"。

### 8.3 凭据与权限

**FR-S16 凭据存储**：API Key、邮箱密码、Webhook Token 一律进系统钥匙串（Keychain / Credential Manager / Secret Service），**绝不落明文配置文件**。
**FR-S17 最小权限**：Skill 与员工都需声明权限，越权在引擎层拒绝。
**FR-S18 高危动作确认**：删除文件、执行脚本、对外发送内容、合并主干、部署上线等必须人工确认，且**不可被自学习或员工自行放开**。
**FR-S19 日志脱敏**：日志中不得出现凭据、完整邮件正文、完整个人信息。
**FR-S20 第三方 Skill/岗位模板风险提示**：导入时明确告知"此 Skill/岗位将访问 X、可能把数据发往 Y、能执行什么命令"。

### 8.4 数据本地性与生命周期

**FR-S21 离线模式（v0.6 修订）**：支持"**不接外部模型**"的离线模式（关闭所有云端外发 + 检测器 + 通知渠道），此模式下**哨兵层全部功能可用**（定时、监测、规则判断、通知），**员工层降级为"不能处理 L2 及以上内容"**，并如实告知用户。

> **明确的能力边界（重要）**：v1.0 不做本地模型，因此"数据不出机器 + 仍能处理敏感内容"**不成立**。产品文案不得宣称"数据不出本机"，只能宣称"**外发前必须脱敏，敏感内容默认拒答**"。
**FR-S22 保留与清理**：原始信号、审计日志、任务时间线各有保留期（默认：信号 30 天、审计 180 天、任务时间线永久可配），支持一键清理。
**FR-S23 导出与迁移**：数据以开放格式导出（SQLite + YAML + Markdown），包含脱敏配置与员工定义。
**FR-S24 卸载**：一键停服务、清自启、可选保留或彻底删除数据。

### 8.5 本机访问控制（v0.7 新增）

这一节回应"同一台电脑被他人使用时，提醒内容与数据会被看到"的隐私关切。
它**不引入账号体系**，只做本机层面的访问控制。

**FR-S25 本机口令锁（可选，默认关闭）**：

| 项 | 约定 |
| --- | --- |
| 用途 | 仅防止同一系统账号下的其他人打开界面查看提醒/历史/数据 |
| 作用范围 | **只锁界面**；daemon 照常运行、提醒照常触发、系统通知照常弹出 |
| 存储 | 口令经强 KDF（如 Argon2id / scrypt）派生后存本地，**绝不明文**；不进钥匙串（钥匙串会被同账号解锁） |
| 联网 | ❌ 完全不联网；无"找回密码"流程（忘记口令 = 清除数据，需二次确认） |
| 自动锁定 | 界面空闲 N 分钟后自动锁定（默认 15 分钟，可配） |
| 与通知的关系 | **锁屏不影响通知展示** —— 若连通知内容也要隐藏，那是"通知内容隐私"设置项（见下） |
| 默认值 | **关闭**（单人使用的电脑不需要它；默认开启会平白增加摩擦） |

**FR-S25b 通知内容隐私（独立开关）**：

- 锁定时，系统通知只显示"你有 1 条提醒"，不显示标题与正文（避免锁屏被别人看到内容）
- 这是**独立于口令锁**的开关（没启口令锁的人也可能坐在别人旁边）

**FR-S26 口令锁不得影响可靠性（硬约束）**：

> ## ⚠️ 无论是否启用口令锁，以下能力必须**完全不受影响**：
> 定时触发、重复规则、休眠唤醒补偿、系统通知投递、崩溃自恢复。
>
> 换句话说：**锁的是"看"，不是"跑"。**

这一条是 §2.4.1 表格里"NFR-R4 断网可用 / NFR-R2 崩溃自恢复"在本机访问控制上的延续 ——
如果实现时发现某个环节必须"解锁后才能继续运行"，那说明设计跑偏了。

**FR-S27 数据目录与系统用户的对应关系**：

- 数据目录建立在当前系统用户下（`~/Library/Application Support/<产品名>/`）
- **不同 macOS 用户账号天然隔离**，不共享、不互访
- 这是本项目的默认多用户方案 —— 不用账号体系来实现"多人使用同一台电脑"

### 9.7 跨平台

| 层面 | 建议方案 | 理由 |
| --- | --- | --- |
| 桌面外壳 | **Electron + TypeScript** | 三平台一致；通知/托盘/自启/钥匙串生态成熟；与现有 Node 24 + pnpm 工具链同构 |
| 备选外壳 | Tauri（体积与内存更优） | 更省资源，但系统集成与调试成本更高；若 NFR-P1/P2 是硬指标则选它 |
| 存储 | **SQLite（WAL）** | 事务保证幂等；看板/任务/审计/预算都是关系型数据；单文件易备份 |
| 配置与定义 | YAML + JSON Schema 校验 | Skill、岗位、流程模板都需人类可读可写可版本管理 |
| 哨兵调度 | 自研 tick 引擎（默认 30 秒）+ 幂等唯一键 + 补偿窗口 | 比 cron 更适合休眠/关机/崩溃场景 |
| 员工编排 | **中央编排器 + 独立 Worker 进程 + 事件总线（本地）** | 故障隔离、可观测、可熔断；避免多 Agent 自由对话的失控 |
| 员工上下文 | 每任务独立上下文 + 从存储重建（无状态 Worker） | 支持崩溃恢复与重试 |
| 代码类隔离 | git worktree / 独立分支 + 文件锁 | 防并发写冲突；合并主干走审批门 |
| 模型接入 | Provider 抽象（OpenAI 兼容 / Anthropic / Ollama / LM Studio）+ 按员工配置模型档位 | 成本与隐私可分层 |
| **知识库/RAG** | 本地优先：**SQLite + 向量扩展（如 sqlite-vec）/ 本地向量库** + BM25（FTS5）混合检索 + 本地 rerank 模型 | 与"数据本地优先"一致；单机自用场景无需独立向量服务；索引可重建 |
| **Embedding** | 本地嵌入模型（如 bge-m3 / nomic-embed）为默认；云端嵌入需显式授权 | 向量可被部分还原，**默认不出机器**（R34） |
| **上下文压缩** | 独立 `ContextManager` 模块：四层模型 + 阈值触发 + 安全断点 + 摘要自检 + 快照落盘；压缩优先用本地小模型 | 压缩是高频操作，必须便宜且可回滚（R37/R40） |
| **脱敏网关** | 独立模块，位于 Provider 层**之前**，引擎层强制唯一出口 | 安全需求的第一实现位；不可作为"可选插件"；**检索结果同样经此出口** |
| 凭据 | 系统钥匙串（Keychain / Credential Manager / Secret Service） | NFR 要求，且支持按员工作用域拆分 |
| 打包分发 | macOS：DMG + 登录项；Windows：安装包 + 计划任务；Linux：AppImage/deb + systemd user unit | 覆盖三平台习惯 |
| 与 DSH 的关系 | 见开放问题 Q1 | 影响架构与工作量，需先定 |

## 11. 数据模型（概念级）

| 实体 | 含义 | 关键关系 |
| --- | --- | --- |
| `Task`（哨兵） | 用户设定的提醒任务 | 1 : N `Occurrence` |
| `Occurrence` | 一次具体触发实例 | 唯一键 (task_id, scheduled_at)，幂等基础 |
| `Monitor` | 监测器实例 | 1 : N `Signal` |
| `Signal` / `Fact` / `Event` | 原始片段 / 去重事实 / 待判断事件 | 逐级归一化 |
| `Policy` / `Skill` | 规则 / 能力包 | Skill 1 : N Policy；带版本 |
| `Notification` / `Feedback` | 投递记录 / 用户反馈 | 驱动学习 |
| `Preference` | 学习得到的偏好画像 | 可人工编辑 |
| `Credential` | 凭据引用（值在钥匙串） | 绑定作用域 |
| **`Role`** | 岗位定义（职责/禁止/工具/DoD/预算） | 1 : N `Employee`；带版本 |
| **`Employee`** | 员工实例 | 绑定 Role、**主团队**、工作区、模型档位、外发级别、凭据作用域、预算 |
| **`Organization`** | 组织根（= 我） | 全局并发上限、全局预算、全局策略（默认单实例） |
| **`Team`** | 团队 = 项目单元 | 含项目、目标、成员、流程模板、工作区、资料库、预算账户、对外接口；1 : N `WorkItem` |
| **`TeamTemplate`** | 团队模板 | 岗位集合 + 流程模板 + 接口约定 + 默认预算；带版本 |
| **`TeamMembership`** | 员工与团队的归属/借用关系 | 主团队 or 借用；借用需时限 + 配额 + 预算归属 |
| **`SharedResource`** | 跨团队共享的员工/工具授权 | 并发上限、时间配额、服务对象记账 |
| **`TeamInterface`** | 跨团队接口契约 | 提供方/调用方/输入输出 schema/验收/SLA/成本承担/版本 |
| **`InterfaceChange`** | 接口变更记录 | 双方确认人、破坏性标记、迁移状态 |
| **`CrossTeamHandoff`** | 跨团队交接单 | = `Handoff` + from/to 团队、interface_id、SLA 截止、成本承担、契约测试结果 |
| **`TeamDependency`** | 跨团队依赖关系 | 谁在等谁、等待时长、是否超 SLA |
| **`WorkflowTemplate`** | 流程模板（阶段/DoD/门/失败策略） | 带版本 |
| **`WorkItem`（看板卡）** | 一张工作项 | 含所属团队、状态、负责人、依赖、交付物、预算、时间线 |
| **`Handoff`** | 交接单 | 关联 from/to 员工、WorkItem、artifacts、verification |
| **`Artifact`** | 交付物 | 带版本、来源、哈希 |
| **`Verification`** | 机械验证记录 | 命令、退出码、输出摘要、时间 |
| **`Run` / `Step`** | 员工执行 / 执行步 | 支撑回放与审计 |
| **`Budget` / `CostRecord`** | 预算与消耗记录 | **四级归因：任务 / 员工 / 团队 / 全局**；跨团队消耗记在成本承担方 |
| **`ApprovalGate`** | 审批门实例 | 待批/已批/已拒 + 决策人 + 理由 + 所属层级（团队级/组织级） |
| **`DataClass` / `RedactionPolicy`** | 分级与脱敏策略 | 版本化 |
| **`OutboundAudit`** | 外发审计记录 | 脱敏项、目标模型、策略版本、**所属团队与员工**（不含原文） |
| **`Software`** | 软件登记项（能力清单） | 名称/版本/路径、能力描述、调用方式、权限、**数据去向**、沙箱可行性、已知坑、准入级别 |
| **`SoftwarePermission`** | 员工 × 软件的可用授权 | 允许的调用方式上限、目录范围、是否可发起申请；可按团队覆盖 |
| **`Invocation`** | 一次软件调用记录 | 员工、软件与版本、命令/动作、参数摘要、耗时、退出码、产物、是否过网关 |
| **`SoftwareRequest`** | 软件申请单 | 用途、现有工具为何不够、来源、版本、权限、许可证、数据去向、风险评级、审批状态 |
| **`InstallJob`** | 安装作业 | 沙箱/主环境、来源与哈希、执行者（自动/人工）、验证结果、回滚点 |
| **`SourceAllowlist`** | 来源白名单 | 包管理器+镜像、官方签名分发、商店、内部源 |
| **`SoftwareBlacklist`** | 黑名单 | 类别/条目/原因；不可被员工或自学习放开 |
| **`TrialRecord`** | 软件试用记录 | 起止、调用次数、失败率、到期结论（保留/卸载/转正） |
| **`ManualGuide`** | 操作引导 | 任务、原因、步骤、预期结果、兜底方案、我确认完成的时间 |
| **`KnowledgeSource`** | 知识来源（文件/网页/邮件/代码库/笔记） | 含层级（个人/团队/组织/外部）、**数据分级**、可信度等级、同步状态 |
| **`KnowledgeDoc`** | 文档实体 | 1 : N `Chunk`；含版本、哈希、有效/更新时间 |
| **`Chunk`** | 知识块（最小检索单元） | 含来源位置（文件+行号/页码）、内容哈希、分级、`generated_by`（人/员工） |
| **`Embedding`** | 向量（本地优先） | 模型名与版本、维度、是否允许出机器 |
| **`Index`** | 关键词索引（BM25）+ 向量索引（ANN） | 可删除重建；原文是唯一真相源 |
| **`Citation`** | 引用指针 | 结论 ↔ Chunk；可解析、可核对、可失效 |
| **`KnowledgeConflict`** | 知识冲突记录 | 冲突双方、裁决规则、裁决人（我）、裁决时间 |
| **`ContextSnapshot`** | 上下文快照 | 压缩前完整上下文，可查看/对比/回滚；保留期可配 |
| **`ContextSegment`** | 上下文分层片段 | 标注所属层（锚定/受保护事实/工作/历史） |
| **`CompressionRecord`** | 压缩记录 | 触发原因、压缩前后 token、被移出内容、摘要、自检结果、所用模型与成本 |
| **`RunLog` / `Heartbeat`** | 运行与心跳记录 | 支撑自监控与诊断 |

## 12. 关键用户流程

### 12.1 首次启动（v0.7 修订：无登录，4 步内可用）

> **前置说明**：本产品**没有登录/注册步骤**（见 §2.4.1）。
> 打开即用；下面是配置向导弹窗，**全部可跳过**，跳过后降级为纯本地提醒模式。

| 步 | 内容 | 可跳过 | 跳过后的默认行为 |
| --- | --- | --- | --- |
| 1 | 语言与主题 | 否（有默认值，直接下一步即可） | 简体中文 + 跟随系统主题 |
| 2 | 通知权限（请求 + 复检；失败则界面常驻警告与手动引导） | 否（不授权则提醒无法触达） | 允许**稍后再问**，但界面持续提示"提醒无法送达" |
| 3 | 开机自启（默认开） | 可 | 不装 LaunchAgent，需手动启动 |
| 4 | **模型与外发级别（可选）** | **可** | **默认「不接外部模型」** —— 纯本地规则模式，全部定时提醒功能可用（见 §12.1.1） |
| — | **本机口令锁（可选）** | **可** | **默认关闭**；同一系统账号下他人可打开界面（见 FR-S25） |

**完成页（关键）**：自动创建一条「**1 分钟后触发**」的示例提醒，并提示
"等它响一次，你就知道它可靠"。这是让用户获得**第一次实证**的设计，不要省略。

#### 12.1.1 「不配置模型也能用」是硬性设计（v0.7 补充）

> ## ⚠️ 模型是**可选增强项**，不是使用前提。
> M1 全部功能（定时提醒、重复规则、休眠补偿、稍后提醒、免打扰、系统通知）**零模型依赖**。

这来自 PRD 的铁律：**LLM 只参与"判断"与"表达"，绝不参与"是否按时触发"。**

| 能力 | 需要模型吗 | 里程碑 |
| --- | --- | --- |
| 定时提醒 / 重复规则 / 系统通知 | ❌ 纯本地规则引擎 | M1 |
| 休眠唤醒补偿 / 稍后提醒 / 免打扰 | ❌ 纯本地 | M1 |
| 自然语言建提醒（"明天9点交周报"） | ✅ 需要 | M3 |
| 邮件/日程重要性判断、每日简报 | ✅ 需要 | M3 |
| RAG 检索 / 员工层 / 团队协作 | ✅ 需要 | M4+ |

**为什么坚持这一点**（三个都很实际）：

1. **可靠性**：模型超时/欠费/改版都不影响提醒 —— 这是 24/7 承诺的前提
2. **零成本起步**：不配 Key = 零 API 花费，可以先当纯提醒工具用很久
3. **零隐私风险**：不接模型 = 数据 100% 不出机器，可先建立信任再逐步放开

**界面上的体现**：未配置模型时，涉及模型的功能显示为"未启用（配置模型后可用）"并提供**一键跳转设置**，
而**不是**显示报错、更不是阻止使用其它功能。

#### 12.1.2 模型配置的入口与形态（v0.7 补充）

模型配置在**设置页**（不在首次启动时强制）：

| 步骤 | 内容 | 安全要求 |
| --- | --- | --- |
| 1 | 选择 Provider（OpenAI 兼容 / Anthropic / DeepSeek；本地 Ollama 保留接口 v1.0 不实现） | — |
| 2 | 填入 API Key | **值直接写入系统钥匙串**；界面**不提供"读取回显"**，只显示"已配置 / 未配置" |
| 3 | 选择默认外发级别（默认最保守：仅 L1 可脱敏外发，L2 需显式开启，L3 永不外发） | 见 FR-S13 |
| 4 | **连通性自检**：发送一次**脱敏后的最小样例**，并**把实际外发内容展示给用户确认** | 见 FR-S12 出站预览 |
| 5 | 设置单日成本上限（默认保守值，超限自动降级为纯规则模式并告知） | 见 FR-D2 |

> **设计红线**：不存在"读取 API Key 返回给界面"的方法。
> 界面只能知道"配没配、是否可用、今日花了多少"，**拿不到凭据本身**。

### 12.2 创建一条提醒

菜单栏 → 新建 → 填标题与时间（或自然语言，M3）→ 保存 → 列表显示倒计时 → 到点弹通知 → 稍后/完成 → 记入历史。

### 12.3 一次监测触发（M2–M3）

采集 → 发现变化 → 生成事实并去重 → 规则命中 → 冷却检查 → 组装通知（M3 经 LLM 判断与措辞，**外发前过脱敏网关**）→ 按渠道分流投递 → 记录 → 用户反馈 → 写入偏好。

### 12.4 睡眠唤醒恢复

唤醒 → 检测时钟跳变 → 扫描补偿窗口内未发实例 → 按优先级排序 → 60 秒内批量补发（合并摘要）→ 写入心跳缺口说明。

### 12.5 导入一个 Skill

选择文件/URL → 解析校验 → **展示权限与预期行为 + dry-run 预览** → 确认 → 落库为草稿 → 手动启用 → 观察期（通知带"新技能"标记）。

### 12.6 创建一个员工（M4）

模板库选岗位（或自定义）→ 填写职责/禁止事项/工作区/工具白名单/DoD/预算/模型档位/外发级别 → **展示权限预览**（它将能访问什么、能执行什么、数据会发往哪里）→ 确认创建 → 员工卡片出现在主界面。

### 12.7 派一个任务给员工（M4）

新建任务（自然语言或结构化）→ 选择负责人 → 系统展示"我打算这么做"的计划 → 开始执行 → 实时可见进度（当前步、已改文件、已花成本）→ 到 DoD 自动跑机械验证 → 汇报（含证据）→ 我确认或打回。

### 12.8 完整交付流水线（M5，对应你的场景）

```
① 我提需求："给登录页加验证码"
        ↓
② PM 员工：写 PRD + 拆任务 + 定义验收标准  →  ⛔审批门：我确认 PRD
        ↓
③ 架构师：技术方案 + 接口定义
        ↓
④ 前端员工 ∥ 后端员工（并行，各自 worktree/分支）
        │  各自跑 build + 单测 通过后才允许交接
        ↓
⑤ 交接给 QA（handoff 单含 commit、验证证据、已知问题）
        ↓
⑥ QA：设计用例 → 执行 → 出测试报告
        ├─ 无 bug ────────────────► ⑦ 回归
        └─ 有 bug → 按归属自动派回 FE/BE → 修复 → 回到 QA 验证
                      （同一任务往返 > 3 次 → ⛔升级通知我）
        ↓
⑦ 回归测试：确认所有 bug 已关闭 + 全量用例通过
        ↓
⑧ 产品验收（PM 员工出验收报告）→  ⛔审批门：我最终点头
        ↓
⑨ 完成，归档交付物与完整时间线
```

**这个流程里的每一条风控都对应一个具体失败场景：**

| 失败场景 | 对应机制 |
| --- | --- |
| 开发和 QA 互相点头说没问题 | FR-G22/G23/G24 机械验证 + 独立验证角色 |
| bug 反复来回修不好，烧一整夜钱 | FR-G16 往返上限 + 无进展熔断 + FR-G28 预算硬上限 |
| 两个开发同时改同一个文件，互相覆盖 | FR-G8 文件锁 + git worktree 隔离 |
| QA 顺手把代码也改了（失去独立性） | 岗位禁止事项 + 引擎层权限拒绝 |
| 员工说"测试通过"其实没跑 | FR-G25 抽查复核 + FR-G14 无证据交接单无效 |
| PRD 写歪了一路错到底 | 阶段 ② 人工审批门 |
| 员工崩了任务丢失 | FR-G33/G35 持久化 + 中断态可重领 |
| 半夜卡住没人知道 | FR-G16 升级 + 哨兵层通知（这就是为什么哨兵层要先做） |

### 12.9 创建一个团队并让两个团队协作（M6）

**建团队**：选团队模板（如"软件项目团队"）→ 填项目名、工作区、预算、成员数量 → **展示权限与资源预览**（将创建哪些员工、能访问哪个目录、月度预算多少、需要哪些凭据）→ 确认 → 团队卡片出现在组织全景。

**跨团队协作（服务式）**：

```
① 博客团队的项目流程跑到"需要设计稿"阶段
        ↓
② 团队编排器发现它 needs 接口 design-assets（接口已声明，无需逐次审批）
        ↓
③ 生成跨团队交接单：from_team=blog, to_team=design, interface=ui-component-delivery,
   sla=3d, cost_bearer=consumer
        ↓
④ 设计团队收到任务，按自己的流程排期执行（博客团队**看不到**设计团队内部看板）
        ↓
⑤ 交付：设计团队回交接单（artifacts + contract_check 机械校验结果）
        ↓
⑥ 博客团队侧做**契约测试**：schema 校验 + 验收标准逐条检查
        ├─ 通过 → 继续自己的流程
        └─ 不通过 → 打回设计团队（计入往返次数，超限升级）
        ↓
⑦ SLA 超时：自动催办 → 二次超时通知我 → 我看到瓶颈并决定插队/改期/换人
        ↓
⑧ 成本：设计团队消耗的 token/时间**记在博客团队预算账户**（按契约约定）
```

**冲突时的样子**：博客团队和另一个团队同时要用"架构师"这个共享员工 → 共享资源并发上限为 1 → 后到的请求排队 → 若两边都标了紧急 → **停在那里等我决定**，而不是自动抢占。

### 12.12 一次外发脱敏（M0）

员工需要把一段含客户信息的文本交给模型 → 网关判定级别（L2）→ 检测到手机号 2 处、身份证 1 处、邮箱 3 处 → 替换为 `[PHONE_1]` `[PHONE_2]` `[ID_1]` `[EMAIL_1..3]` → 记录审计 → 外发 → 模型返回含占位符的结果 → **本地还原真实值** → 交付给员工/我。
我可在审计页看到"这次发了脱敏后的什么内容"，也可全局关闭云端外发。

### 13.3 反指标（出现即视为设计失败）

- 用户因为"太吵"而整体静音或卸载
- 因 LLM 失败导致定时提醒漏发（一次即严重缺陷）
- **任何一次 L2/L3 数据明文外发**
- 员工跑了一整夜、花了几十美元、产出不可用
- 员工之间无限往返、无人知晓
- 用户无法解释"它为什么这么做"
- 员工绕过权限改了他不该改的东西
- **一个团队的失败拖垮另一个团队（项目串味 / 全局阻塞）**
- **跨团队账单算不清，我不知道钱花在哪个项目上**
- **共享员工被两个团队同时抢，导致两边都半途而废**
- **员工在我不知情的情况下装了软件、扩展或包**
- **软件读到的东西绕过脱敏网关直接发给了模型**
- **GUI 自动化把屏幕（含敏感信息）截图外发**
- **员工通过自动化复用我的登录态，绕过权限干了我没授权的事**
- **它在知识库里没有依据，却编了一个很像样的答案**
- **引用是假的或指不到原文**
- **团队 A 的项目资料被团队 B 的员工检索到了**
- **压缩之后它把"讨论过"说成"已经决定"，或把数字记错了**
- **压缩把禁止事项弄丢了，于是它做了本来不该做的事**

| **R35** | **检索到的是员工自己写的、未经验证的内容 → 自我强化幻觉** | 高 | `generated_by=employee` 标签 + 检索降权 + 不可作为唯一依据 + 冲突上报裁决 |
| **R36** | **无依据却编造（幻觉的主要表现形式）** | **极高** | 证据不足必须明说 + 引用强制可解析 + 机械校验引用可核对 + 抽查指标 = 0 |
| **R37** | **上下文压缩丢关键约束 → 员工做了不该做的事** | **极高** | 四层模型：锚定层与受保护事实层**逐字保留**；压缩后哈希自检；不通过则回滚重压；禁止在有损摘要里放约束 |
| **R38** | **压缩本身引入幻觉（把推测写成结论）** | 高 | 摘要不得引入原文没有的信息；不确定内容显式标注；压缩前快照可对比复核 |
| **R39** | **知识库变成新的敏感数据囤积地（越灌越多、越难清理）** | 中 | 入库前脱敏 + 分级标签 + 保留期与软删除 + 一键清理某来源 + 原文是唯一真相源（索引可重建） |
| **R40** | **上下文压缩的额外成本（压缩也要调用模型）** | 中 | 优先本地小模型压缩；压缩成本计入预算；缓存阶段摘要避免重复压缩 |

### 16.2 里程碑验收清单模板（每个功能上线前必答）

1. 断网时是否正常？
2. 系统休眠 8 小时后唤醒是否正常？

5. 失败时用户是否**看得见**（而非静默失败）？
6. 是否占用可感知的 CPU / 电量 / 金钱？
7. 是否可一键关闭 / 卸载干净？
8. **（员工层）它的"完成"是否有机械验证证据？**
9. **（员工层）它有没有可能绕过权限或脱敏网关？**
10. **（员工层）它超预算/卡住/循环时会不会主动停下来找我？**
11. **（软件）它调用的软件是否已登记在能力清单里、调用方式是否是最稳定的那一档？**
12. **（软件）它有没有可能在没告知我的情况下装了什么（软件/扩展/依赖）？**
13. **（软件）它读到的数据、以及它给我看的东西，是否都过了脱敏网关？**
14. **（软件）调用失败时它会不会静默失败，还是走降级链 / 给我操作引导？**
15. **（知识）这条基于内部资料的结论，引用是否可解析、原文是否可核对？**
16. **（知识）知识库里没有依据时，它是承认还是编？**
