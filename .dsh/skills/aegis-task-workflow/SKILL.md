# Aegis 开发任务工作流

## 1. 标准五步流程（每个改动都适用）

```
① 定位  → ② 设计判据 → ③ 实现 → ④ 验证 → ⑤ 提交
```

| 步 | 做什么 | 产出物 | 完成判据 |
| --- | --- | --- | --- |
| **① 定位** | 明确改动属于哪层/哪个包；检查是否触碰已确立约束 | 一句话说明"改什么、在哪改" | 能回答 `aegis-engineering-standards` §1 的四个问题 |
| **② 设计判据** | 先想"怎么证明它对了"，再动手写实现 | 测试用例清单（正常/幂等/边界/恢复） | 每条判据都能自动化 |
| **③ 实现** | 按判据写代码与测试 | 带中文注释的实现 + 测试 | 本地 `pnpm test` 通过 |
| **④ 验证** | 跑全量门禁 + 端到端确认 | `pnpm verify` 全绿 + 必要时手工验证 | 见 §3 的验收清单 |
| **⑤ 提交** | 按粒度拆分提交 | 符合规范的提交 | `git log` 可读、可定点回滚 |

**最关键的是第 ② 步。** 先写实现再想测试，会导致测试只覆盖"实现碰巧做对的部分"。

## 2. 里程碑工作流（R2、R3…）

里程碑比单个改动多两层：**开工检查**与**收尾验收**。

### 2.1 开工前（Gate：不满足就不要开始）

- [ ] 上一个里程碑的验收已完成（`pnpm verify` 全绿 + 端到端验收通过）
- [ ] 本里程碑的范围已在 `README.md` 里写明
- [ ] 依赖的技术前提已验证（spike 通过 / 前一阶段已交付）
- [ ] 已知的关键约束已列在 `README.md` 的"已确立的关键技术事实"里
- [ ] 有明确的**验收门槛**（可自动化的判据，而不是"感觉能用"）

### 2.2 收尾时

- [ ] 里程碑的验收门槛全部通过
- [ ] `README.md` 的里程碑表格更新为已完成
- [ ] 端到端演示可复现（写进 README 或交付报告）
- [ ] 新增的约束/踩坑记录已写入 `README.md` + 原地注释
- [ ] 打 tag（如 `git tag -a r2 -m "R2 调度引擎完成"`）

## 3. 验收清单（每个改动通用）

```bash
pnpm verify        # ① 必须全绿
```

然后逐项确认（**门禁挡不住的部分必须人眼看**）：

- [ ] 需求/判据是否真的被满足了（不是"测试过了"而是"行为对了"）
- [ ] 失败时会怎样？用户能看见吗？
- [ ] 重复执行会怎样？进程中途被杀会怎样？
- [ ] 有没有引入新的约束需要记录？
- [ ] 文档（README / 设计文档 / 技能）是否同步？

**必要时做端到端验证**（尤其是 IPC、启动序列、平台能力）：

```bash
# 例：验证 daemon 启动序列
node apps/daemon/dist/main.js --data-dir "$(mktemp -d)" --check
```

单元测试证明"零件对"，端到端验证证明"装起来对"。**两者都要。**

## 4. 每个里程碑的固定节奏

| 阶段 | 动作 |
| --- | --- |
| 开工 | 按 §2.1 过检查单；必要时先做 spike 排风险 |
| 实现 | 按依赖顺序做（底层优先），每个模块完成即 `pnpm verify` + 提交 |
| 中途 | 发现新约束 → **立刻**写进 README + 原地注释（不要攒到最后） |
| 收尾 | 按 §2.2 过检查单；写交付报告（做了什么、怎么验证的、遗留什么） |
| 交付 | 向用户报告：结果、验证方式、需用户决策的项 |

**不要在里程碑中途攒一个大提交。** 每个模块完成就提交，这样：
- 任意时刻都有可回退的可用状态
- 出问题能二分定位
- 交付报告可以直接从 `git log` 生成

## 5. 遇到阻塞怎么办

| 阻塞类型 | 处理 |
| --- | --- |
| **需要用户决策**（如产品名、预算额度） | 不要停下来等 —— 用可逆的默认值继续，把决策点**明确列出**留待确认 |
| **环境限制**（沙箱禁止写系统目录） | 显式标注为 `blocked`（不是 `fail`），准备一份用户可执行的验证脚本 |
| **技术前提不成立**（spike 失败） | **停下来**，先给出替代方案与影响面，再决定是否继续 |
| **范围蔓延**（发现"顺手也该做"） | 记入 backlog（写进 README 的后续计划），**不在本次做** |

**原则**：只有"技术前提不成立"值得停下；其余都应当找可逆路径继续推进。

## 6. 反模式（本项目明令禁止）

| 反模式 | 为什么禁止 | 正确做法 |
| --- | --- | --- |
| 先写实现，回头补测试 | 测试会变成"给实现背书" | 先定判据 |
| 一个提交包含整个里程碑 | 无法评审、无法定点回滚 | 按模块拆 |
| 攒着约束不记录 | 下个会话就忘了 | 踩到就写 |
| 为了过门禁而加白名单 | 门禁失去意义 | 补注释/补依赖声明，或改门禁逻辑并说明原因 |
| 静默跳过失败用例 | 报告失真 | `skipIf` + 记录事实 |
| "顺手优化"无关代码 | 污染 diff、引入风险 | 单独提交 |
| 用 `--no-verify` 绕过 hook | 规范形同虚设 | 修 hook 判断逻辑 |

## 7. 交付报告模板

里程碑结束时向用户报告，包含：

```markdown
## 结果
一句话说明达成了什么。

## 验证方式（不是"应该没问题"）
| 检查 | 结果 |
表格列出：门禁、测试数、端到端验证、以及如何复现 |

## 过程中发现并修掉的问题
列出真实的缺陷与根因（这部分最有价值）。

## 新确立的约束
列出写入 README 的条目。

## 需要你决策/留意的事
明确列出，并给出建议值与影响。
```
