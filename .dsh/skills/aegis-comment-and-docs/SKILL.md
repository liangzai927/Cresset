# Aegis 注释与文档规范

> **本项目的一条硬规则：不写注释的代码视为未完成。**
>
> 理由不是"好看"，而是这个项目要在无人看管下运行数月。半年后回头排查一次凌晨三点的静默失败时，
> **唯一能告诉你"这里为什么这么写"的，就是注释**。代码只能说明"做了什么"，注释才能说明"为什么这样做、以及为什么不那样做"。

## 1. 注释必须用中文

- 注释、JSDoc、文档、提交信息正文：**一律简体中文**。
- 标识符（变量/函数/类型/表名/列名）：**英文**，遵循 `aegis-engineering-standards` 的命名约定。
- 既有英文注释（如从上游抄来的）不必强行翻译，但**新增内容一律中文**。
- 专业术语可保留英文（如 `WAL`、`UDS`、`idempotent`），但首次出现宜给出中文解释。

## 2. 必须写注释的六类位置（缺一即视为未完成）

### 2.1 所有导出符号（强制，且有机械检查）

每个 `export` 的函数、类、接口、类型、常量都要有 JSDoc：

```ts
/**
 * 原子领取一个待派发实例（幂等的第二道闸）。
 *
 * ⚠️ 只有把 state 从 'pending' 改成 'claimed' 成功者才拥有派发权；
 *    影响行数为 0 时必须放弃，**不得**依据内存状态继续派发。
 *
 * @param id 实例 id
 * @param ttlMs 领取超时；超时后由 reconcileStaleClaims 置为 unknown
 * @returns claimed=false 表示无需派发（已被别人领走或已发送过）
 */
claim(id: string, ttlMs: number = DEFAULT_CLAIM_TTL_MS): ClaimResult
```

### 2.2 "为什么"而非"是什么"

代码已经说明了"是什么"，注释要补的是**决策理由**与**被否决的替代方案**：

```ts
// ✅ 好：解释了反直觉的选择
// 这里刻意用原生 setInterval 而不是 clock.setInterval：
// Clock 的实现对定时器做了 unref（库代码不应阻止进程退出），
// 而 daemon 作为常驻进程必须持有至少一个 ref 的句柄，否则事件循环清空即退出。

// ❌ 差：把代码翻译了一遍
// 设置一个 60 秒的定时器
setInterval(fn, 60_000);
```

### 2.3 约束与踩坑记录（本项目最有价值的注释）

凡是踩过的坑，都要在原地留下"坑的说明 + 后果 + 正确做法"。已有大量先例：

```ts
/**
 * ⚠️ 必须显式指定钥匙串（约束 C-9）。
 * 不带 -k 时 `security` 会在整个搜索列表（login + System + 其他）中查找，
 * 命中哪个钥匙串并不确定 —— R1 实测出现过"delete 报告已删除、find 仍能检索到"。
 */
```

引用约束编号（`C-1`…`C-9`）或需求编号（`FR-A3`、`NFR-SP4`）能让后来者追溯原始理由。

### 2.4 复杂或易错逻辑（就近说明）

- 非直观的位运算、正则、SQL、时间计算、并发控制：**逐段说明意图**。
- 正则必须解释匹配目标与边界，例如：

```ts
/** 中国大陆身份证：18 位（末位可为 X），带校验位 */
const ID_CARD_RE = /(?<!\d)[1-9]\d{5}(?:19|20)\d{2}(?:0[1-9]|1[0-2])(?:0[1-9]|[12]\d|3[01])\d{3}[\dXx](?!\d)/g;
```

### 2.5 文件头注释（每个源文件都要有）

说明**这个文件的职责边界**，以及它**不做什么**（后者往往更重要）：

```ts
/**
 * 任务 DAO
 *
 * 约定：
 *   - 行的读取**一律经 Zod 解码**，任何格式漂移都会在边界暴露
 *   - 布尔在 SQLite 里是 INTEGER，出入库都要显式转换（不要依赖真值判断）
 *
 * 本文件不负责：调度计算（属 scheduler）、实例幂等（属 occurrence-dao）
 */
```

### 2.6 明确的"暂不实现"

写了简化实现或留了缺口，必须写明**为什么现在不做**以及**什么时候补**：

```ts
// R1 仅统计待补数量，不做实际派发 —— 派发属 M1 调度器（R2）
```

## 3. 禁止的注释类型

| 反模式 | 例子 | 为什么禁止 |
| --- | --- | --- |
| 复述代码 | `// 递增计数` 配 `count++` | 零信息量，且会随代码改动腐化 |
| 情绪化/无信息 | `// 这里很坑`、`// 不要动` | 没说明"坑在哪"，后人只能猜 |
| 注释掉的死代码 | `// const old = ...` | 用 git 历史，不要留在源码里 |
| 与代码矛盾 | 注释说"3 秒"、代码写 5 秒 | 比没有注释更危险 |
| 空 JSDoc 占位 | `/** TODO */` | 等于没写 |

**判断标准**：删掉这条注释，读者是否会丢失信息？如果不会，就删掉。

## 4. JSDoc 标签使用约定

只使用有实际价值的标签，不要为了"齐全"而堆砌：

| 标签 | 何时用 |
| --- | --- |
| `@param` | 参数语义不自明时（有单位/有边界/有副作用时必须写） |
| `@returns` | 返回值有特殊语义时（如"返回 null 表示不存在，而非错误"） |
| `@throws` | 会抛领域错误时，说明**什么条件下抛** |
| `@example` | 公开 API 或用法不直观时 |
| `⚠️` 前缀段落 | 表示"这里有坑/这是硬约束"，本项目大量使用 |
| `@deprecated` | 标记弃用并给出替代方案 |

## 5. 文档更新的时机（不是"以后补"）

| 改动类型 | 必须同步更新的文档 |
| --- | --- |
| 新增/修改跨包或跨进程契约 | `packages/contracts` 或 `ipc-contract` 的注释 + 相关设计文档 |
| 新增数据库表/列/索引 | `M0+M1详细设计.md` §4 的 DDL 段落 |
| 新增约束（踩坑后） | 本仓库 `README.md` 的"已确立的关键技术事实"+ 原地注释 |
| 改变架构决策 | 对应 ADR（`技术选型与架构设计.md` §7） |
| 新增命令/流程 | `README.md` 的常用命令表 |
| 改变验收标准 | `M0+M1详细设计.md` §9 的用例清单 |

**原则**：文档与代码在**同一个提交**里更新。分开提交等于永远不更新。

## 6. 机械检查（本项目已落地）

`pnpm verify` 中已包含注释覆盖率检查（`tools/check-comments.mjs`）：

- **导出符号必须有 JSDoc**：缺失即失败（这是硬门禁）
- **每个源文件必须有文件头注释**：缺失即失败
- 注释行占比：作为**报告项**而非硬门禁（避免为凑数写废话注释）

运行方式：

```bash
pnpm comments          # 只跑注释检查，看当前缺口
```

出现失败时的正确做法是**补注释**，而不是在检查脚本里加白名单 —— 除非该符号确实自明（如纯类型别名 `export type Foo = Bar`），此时应在脚本的豁免规则中**写明理由**。

## 7. 注释质量自查（写完问自己）

1. 半年后的我，能否只看注释就明白**为什么**这么写？
2. 这条注释是否记录了**被否决的方案**？如果当初有纠结，写下纠结的原因。
3. 如果这是踩坑记录，是否包含：现象 → 根因 → 正确做法 → 引用编号？
4. 是否有"注释说了但代码没做"的矛盾？（这比缺注释更糟）
5. 删掉任何一条，读者会丢失信息吗？不会的话删掉它。
