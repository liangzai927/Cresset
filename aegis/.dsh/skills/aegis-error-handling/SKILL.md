# Aegis 错误处理与失败可见性

> **本项目把"静默失败"列为头号缺陷类型。**
> 一个 24 小时常驻的程序最危险的失败方式不是崩溃（崩溃会被发现），
> 而是**安静地不再工作** —— 用户以为提醒还在，实际早就停了。

## 1. 禁止静默失败（PRD NFR-W2）

任何失败必须有**至少一个**出口：

| 出口 | 适用 |
| --- | --- |
| 抛出领域错误 | 调用方必须处理的情况（如"外发被拒绝"） |
| 记录结构化日志 | 可自愈的失败（如一次重试失败） |
| 落库为状态 | 需要后续处理或用户可见的失败（如 `occurrence.state='failed'`） |
| 对用户可见 | 影响承诺的失败（如"通知渠道不可用"必须出现在界面上） |

### 1.1 空 catch 的唯一合法形态

```ts
// ✅ 合法：清理路径，且必须写明为什么可以忽略
try {
  rmSync(paths.handshakeFile, { force: true });
} catch {
  /* 关闭流程中清理失败不影响结论：文件可能已被其他路径删除 */
}

// ❌ 非法：吞掉了一个可能有后果的失败
try {
  await notifyUser(msg);
} catch {}
```

**判断标准**：忽略这个错误，会不会导致"用户以为成功但实际没做"？会 → 不允许空 catch。

## 2. 领域错误类型（而不是裸 Error）

每种可预期的失败定义具名错误类，携带**结构化信息**：

```ts
export class OutboundBlockedError extends Error {
  readonly decision: OutboundDecision;   // 携带决策详情，便于上层展示"为什么被拒"
  constructor(decision: OutboundDecision) {
    super(`外发被拒绝（${decision.dataClass}）：${decision.reason ?? "策略不允许"}`);
    this.name = "OutboundBlockedError";
  }
}
```

已有的领域错误类型（新增时保持一致风格）：

| 错误 | 位置 | 含义 |
| --- | --- | --- |
| `MigrationError` | storage | 迁移失败 / checksum 不匹配 / 库版本超前 |
| `SecretUnavailableError` | secrets | 凭据存储不可用 |
| `SecretWriteError` | secrets | 凭据写入失败 |
| `AlreadyRunningError` | daemon | 已有实例在运行 |
| `OutboundBlockedError` | redaction-gateway | 外发被策略拒绝 |
| `RpcError` / `ProtocolMismatchError` | ipc client | IPC 层错误 |

**约定**：`error.name` 必须显式设置（否则日志里全是 `Error`，无法区分）。

## 3. 异常消息不得含敏感值

```ts
// ❌ 典型错误：把凭据写进了异常消息（会进日志、可能进审计）
throw new Error(`写入失败：${JSON.stringify(credentialValue)}`);

// ✅ 只带定位信息
throw new SecretWriteError(r.stderr || r.stdout || `security 退出码 ${r.code}`);
```

同理：**`catch (err) { log(err.message) }` 之前要确认 err.message 不含敏感值**。

## 4. 降级链（有顺序、有终止）

失败的下一步不是"放弃"，而是**按预定链条降级**，且链条必须有限：

```ts
// 通知投递的降级链（R2 会实现）
os_notification → （失败/超时）→ cli_fallback（osascript）→ 落库为 failed + 生成 failure 通知
```

**规则**：

1. 每一级都记录尝试（`delivery_attempt` 表）
2. 降级不是静默的 —— 全部失败要生成"关于失败的通知"
3. 链条必须有终点，禁止无限重试
4. 降级不得降低安全等级（例：不允许"外发失败就跳过脱敏"）

## 5. 重试与退避

| 场景 | 策略 |
| --- | --- |
| 瞬时错误（网络/忙） | 指数退避 `2^n * baseMs`，上限封顶（如 5 分钟），最大尝试次数明确 |
| 永久错误（权限/不存在） | **不重试**，直接降级或失败 |
| 超时 | 视为瞬时错误，但记录 `outcome='timeout'` 以便区分 |
| 幂等操作 | 可安全重试；**非幂等操作必须先设计幂等键**再谈重试 |

**所有超时必须显式设定**（尤其是会阻塞无人值守场景的调用，如钥匙串读取）。

## 6. 启动期失败的处理

启动序列中，不同阶段的失败策略不同：

| 阶段 | 失败策略 | 理由 |
| --- | --- | --- |
| 单实例锁被占 | 退出码 **0** + 说明 | 不是错误，是正常情况（脚本可无脑调用） |
| 配置缺失/损坏 | 用默认值 + **明确报告问题** | 不该因为配置问题起不来 |
| 迁移失败 | **直接失败退出** | 结构不一致时继续运行会造成数据损坏 |
| 审计写入失败 | 记录并继续 | 审计失败不应阻断主流程，但必须可见 |
| IPC 监听失败 | 释放锁 + 关库 + 退出 | 无法被连接等于不可用，必须退出让看门狗重启 |

## 7. 崩溃兜底

```ts
// 顶层：捕获未处理异常并留下痕迹，然后以非 0 退出（交给看门狗重启）
main().catch((err: unknown) => {
  process.stderr.write(JSON.stringify({ event: "daemon.fatal", error: ... }) + "\n");
  process.exit(1);
});
```

**约定**：崩溃路径必须打印**结构化 JSON**（而不是裸字符串），这样日志收集端能直接解析。

## 8. 用户可见性矩阵

| 失败类型 | 界面呈现 |
| --- | --- |
| 通知渠道不可用 | 状态条显示"降级" + 原因 |
| 监测器连续失败 | 指标页显示失败率 + 最近错误 |
| 预算超限 | 暂停任务 + 通知（不允许静默继续烧钱） |
| 配置使用了默认值 | 设置页提示 + `degradedReasons` 字段 |
| 运行缺口（我停过） | 顶部告警条 + 一条 `system_gap` 通知 |
| 投递失败 | 历史记录标红 + 失败横幅 |

**新增失败类型时，必须同时决定"用户在界面哪里能看到它"** —— 答不出来就说明设计不完整。

## 9. 自查清单

写完错误处理，过一遍：

- [ ] 每个 `catch` 都有出口（日志/抛错/状态）或有明确理由的空实现
- [ ] 异常消息不含凭据或原文
- [ ] 具名错误类设置了 `name`
- [ ] 重试有上限、有退避、有终止条件
- [ ] 降级链的每一级都被记录
- [ ] 失败在界面上有可见位置（或明确说明为什么不需要）
- [ ] 超时已显式设定
