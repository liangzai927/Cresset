# Aegis 代码审查规范

> **为什么单人项目也要写 review 规范**：写代码的人和审查代码的人如果是同一个大脑，
> 就会系统性地漏掉同一类问题。这份清单的作用是**把一个不同的视角固化下来** ——
> 即使执行者还是你。

## 1. 审查顺序（先看不可逆的，再看可改的）

```
① 安全与数据（不可逆） → ② 可靠性语义 → ③ 契约与兼容性 → ④ 可测试性 → ⑤ 可读性与风格
```

理由：前两类出问题的代价是事故（数据泄露、用户漏提醒），后三类出问题的代价是维护成本。

## 2. 第一类：安全与数据（任一不通过即打回）

- [ ] 有没有**新增外发路径**绕过 `redaction-gateway`？
- [ ] 敏感值是否可能进入日志 / 审计 / 异常消息 / 命令行参数？
- [ ] 凭据读取是否带 `-w` 且显式指定钥匙串？（约束 C-5 / C-9）
- [ ] 新增文件是否需要 `0600`？
- [ ] 数据库写入前是否经过 Zod 校验？（否则脏数据落库）
- [ ] 迁移是否是**新增**的？已发布的迁移有没有被改动？（checksum 锁会拦，但要在 review 时确认意图）
- [ ] 有没有把真实个人数据写进测试样本？（必须是构造数据）

## 3. 第二类：可靠性语义

- [ ] **幂等**：重复调用会不会产生重复副作用？是否有唯一索引/影响行数裁决？
- [ ] **时间**：是否走了注入的 `Clock`？有没有直接 `Date.now()`？
- [ ] **类方法传参**：是否用箭头函数包装（避免丢 `this`）？
- [ ] **失败可见**：这个失败用户能看到吗？有没有静默吞掉？
- [ ] **降级链**：重试有上限吗？有退避吗？链条有终点吗？
- [ ] **超时**：会阻塞无人值守场景的调用是否设了超时？
- [ ] **崩溃恢复**：进程在中间步骤被杀会怎样？状态能收敛吗？
- [ ] **并发**：两个 tick / 两个连接 / 两个进程同时进来会怎样？
- [ ] **外部实例/迁移**：有没有旧 checkout 的 daemon 占着 socket/数据目录？握手 `daemonEntry` 是否与当前入口一致？

## 4. 第三类：契约与兼容性

- [ ] 跨包/跨进程结构变了，是否同步了 Zod schema 与两侧使用者？
- [ ] IPC 方法变了，是否考虑 `PROTOCOL_VERSION`？
- [ ] 数据库结构变了，老用户的库能平滑升级吗？
- [ ] 是否暴露了**数据库行类型**给外部（应当用 View 类型）？
- [ ] 破坏性变更是否在 commit body 里写明了迁移步骤？
- [ ] 断言有没有"两端 undefined"的假通过？（尤其是跨进程字段透传）

## 5. 第四类：可测试性

- [ ] 新逻辑有对应测试吗？
- [ ] 修 bug 是否补了**能复现该 bug** 的测试？
- [ ] 时间相关逻辑是否用 `VirtualClock` 而不是真等待？
- [ ] 失败路径有测试吗（不只是正常路径）？
- [ ] 测试是否清理了临时资源（目录/连接/钥匙串项）？

## 6. 第五类：可读性与风格

- [ ] 每个导出符号有中文 JSDoc 吗？（`pnpm comments` 会拦）
- [ ] 有文件头注释说明职责边界吗？
- [ ] "为什么"写在注释里了吗（尤其是反直觉实现）？
- [ ] 命名是否有语义？有没有 `data`/`temp`/`utils` 这类命名？
- [ ] 函数是否过长（>60 行）、嵌套是否过深（>3 层）、参数是否过多（>4 个）？
- [ ] 有没有留下 `TODO` 却没说清"为什么现在不做"？

## 7. 本项目的高频缺陷模式（重点盯这些）

这些是**实际发生过**的问题，盯住它们能挡住大部分回归：

| 模式 | 表现 | 防法 |
| --- | --- | --- |
| **检查后写入的竞态** | 先 SELECT 再 INSERT/UPDATE | 用唯一索引 + `ON CONFLICT` / `WHERE state=?` |
| **类方法丢 this** | `fn(obj.method)` → `#private undefined` | 箭头函数包装 |
| **写入前未校验** | 脏数据落库，读回时才炸 | 入参先 Zod |
| **空 catch 吞掉后果** | 用户以为成功，实际没做 | catch 必须有出口 |
| **异常消息带敏感值** | `throw new Error(JSON.stringify(secret))` | 只带定位信息 |
| **只在读回时校验** | 与上面同源 | 进出都校验 |
| **测试数据本身不合法** | 断言正确行为却失败（如身份证校验位错） | 用脚本生成合法样本 |
| **沙箱/环境相关用例静默跳过** | 报告显示"通过"但实际没跑 | `skipIf` + 记录事实的断言 |
| **依赖边漏登记** | 类型过了、构建过了、运行时崩 | 四步同步 + `pnpm resolve` |
| **注释与代码矛盾** | 注释说 3 秒、代码写 5 秒 | review 时对照检查 |

## 8. 自我审查的具体方法（对抗盲区）

写完代码后，用这三个动作过一遍：

### 8.1 "反向阅读"法

**不要**按自己写的顺序读。从最后一行的收尾逻辑往前读，或者从测试文件往实现读。
按原顺序读会重现你写作时的思维路径，等于没审。

### 8.2 "假设它错了"法

挑三个具体场景，问"如果这里错了会怎样"：

1. 这个操作执行到一半进程被杀
2. 这个方法被并发调用两次
3. 系统时间被往前调了 3 小时

答不上来，说明这个改动还缺测试或缺少防御。

### 8.3 "新人视角"法

假装你从未见过这段代码，只看**注释和函数签名**，能否说出：

- 它做什么？
- 它不做什么？
- 失败时会怎样？

说不出来 → 注释不够（回到 `aegis-comment-and-docs`）。

## 9. 审查结论的三种措辞（避免模糊）

| 结论 | 含义 | 后续 |
| --- | --- | --- |
| **通过** | 可以合并 | 直接提交 |
| **有条件通过** | 必须修 X（列出具体项） | 修完即可，无需重审 |
| **打回** | 方向或安全有问题 | 说明原因 + 建议方向，重新设计 |

**禁止**："看起来还行"、"应该没问题"、"回头再说" —— 这些措辞会让问题流进 main。

## 10. 与自己协作的实际做法

- **隔一段时间再审**：写完立刻审容易顺着原思路走。可以先做别的（或跑一次 `pnpm verify`）再回来。
- **用 `git diff` 审，不要用编辑器**：diff 视角更容易发现"顺手改坏的东西"。
- **让门禁先说话**：`pnpm verify` 能挡住的（类型/lint/注释/依赖方向）不要靠人眼。
  人眼应当集中在门禁挡不住的地方：**语义、竞态、失败路径、契约兼容性**。
